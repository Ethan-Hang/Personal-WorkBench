## 1. 产品定位

Research Workbench 是 Personal WorkBench 内一个独立的论文管理、阅读与研究知识整理领域。
它不是 Zotero 的附属品，也不以 Zotero 数据库作为内部真相来源。

产品应当拥有自己的数据模型、文件管理、PDF 阅读、批注、检索和研究工作流。Zotero、
BibTeX、RIS、CSL JSON 等只位于互操作边界，用于迁移、导入、导出和必要的生态兼容。

目标工作流是：

```text
采集 / 导入
    → 去重与元数据确认
    → 文献库、目录与标签
    → PDF 阅读与上下文批注
    → 证据、观点与跨论文对照
    → 综述、写作和研究项目推进
```

产品差异化不来自“比 Zotero 多几个按钮”，而来自两点：

1. 更清晰、可恢复、不会重复占用空间的文件与知识组织方式。
2. 把“读过和高亮过”继续推进为可追溯的证据、观点和写作材料。

## 2. 当前已确认的痛点

### 2.1 文件保存与分类

- 同一 PDF 可能服务多个论文、课程或研究项目，不应因为出现在多个层级目录而重复保存。
- 同一 PDF 在不同研究目的下需要不同批注，不能被迫共享唯一一套标注。
- 文件夹树必须清晰直观，移动、添加到其他目录和删除引用的语义不能含糊。
- 文件去重不能破坏用户对论文版本、所属项目和阅读上下文的理解。

### 2.2 标签创建、治理与找回

- 标签入口过小或创建步骤繁琐会打断阅读。
- 标签长期积累后容易出现大小写、语言、单复数和近义词造成的重复。
- 标签如果只以大量小色块平铺，数量增加后无法浏览和维护。
- 用户有时记得概念或近义表达，却想不起当时使用的准确标签。

### 2.3 PDF 资源开销

- 打开过多 PDF 后，后台标签页不应持续占用完整渲染内存。
- 大型文档的解析、页面渲染、全文索引和 OCR 不应在打开瞬间同时争抢 CPU。
- 关闭或休眠文档后，页面 Canvas、文本层和中间缓存必须能够回收。

### 2.4 论文类型与引用元数据

- 论文、报告、预印本、标准、网页和其他材料不一定能落入严格的固定分类。
- 不完整或不规则来源不能因为缺少“正确类型”而无法保存。
- 作者、日期、载体、版本和标识符等引用信息需要灵活保存，并保留来源与原始字段。
- 引用输出格式不应反过来限制内部数据模型。

### 2.5 基础能力底线

- 基本 PDF 阅读器能力不能缺失。
- Zotero 已被验证有效的文献管理能力不能因为产品追求差异化而丢失。
- 兼容 Zotero 是次要目标，但用户的数据必须可迁移、可导出，不能形成新的锁定。

## 3. 已确认的产品原则

### 3.1 WorkBench 是数据真源

Research Workbench 自己管理论文、元数据、附件索引、阅读状态、批注和研究知识。
外部平台 ID 只用于建立映射，外部数据不得直接决定内部表结构。

### 3.2 论文、文件和上下文分离

“学术作品”“某一版本”“磁盘上的文件”“目录中的位置”和“为了某个目的阅读”是不同概念。
不能用一条记录或一个目录路径同时承担这些职责。

### 3.3 原始文件默认不可变

批注、笔记和阅读状态默认旁挂保存，不直接修改原 PDF。需要分享时可显式导出带批注副本。
这样才能可靠去重、校验文件完整性，并避免第三方工具写回导致原件变化。

### 3.4 本地优先、可恢复、可迁移

- 离线时仍能管理、阅读、搜索已有内容。
- 原始 PDF、元数据、批注和笔记都有明确导出路径。
- 导入、合并、移动和删除等高风险动作应可预览或撤销。
- 数据库损坏不能连带破坏原始附件。

### 3.5 性能是功能约束

大型 PDF、多文档标签页和长时间阅读是正常场景，不是事后优化项。实现前必须建立测试语料和
测量首次打开、翻页、搜索、峰值内存、后台休眠及关闭后回收等指标。

### 3.6 视觉原型不构成约束

与 `TASK-013` 关联的视觉材料仅用于说明“论文项目、阶段、研究资产、导师意见”等可能的
信息结构。最终导航、布局、步骤数量、进度表达和交互方式均需根据真实阅读工作流重新设计。

### 3.7 跨平台与运行形态

首版继续采用浏览器界面 + 本地 server，不引入桌面外壳。Windows 和 macOS 是正式支持平台，
Linux 作为兼容目标，在文件路径、进程启动、PDF 能力和凭据存储等平台差异上避免主动封死。
未来若转为 App，应作为完整运行形态迁移单独设计，不在当前方案中预埋半套桌面实现。

跨平台验证以具体测试模块为单位。只有涉及文件系统、路径、进程、凭据存储或原生依赖的平台相关模块，才维护
对应的平台测试矩阵；不要求每个切片在不同平台重复整条产品流程。一个模块可以先在当前开发平台完成实现和测试，
另一平台的同模块结果保留为待测，不阻塞无关模块。若同一模块先在 Windows 验证，之后补 macOS；先在 macOS
验证时则补 Windows。每条兼容性记录必须写明测试模块、操作系统、架构、文件系统、Node.js 版本和测试日期；
没有运行过的平台明确标为“未实测”，不能从路径语法检查或其他平台结果推定为通过。

## 4. 领域概念草案

下表用于稳定讨论语言，不等同于最终数据库表。

| 概念                | 职责                                                                         |
| ------------------- | ---------------------------------------------------------------------------- |
| `Work`              | 一项学术作品或研究材料的稳定身份，例如论文、报告、标准或网页                 |
| `Edition`           | 作品的具体版本，例如 arXiv 预印本、会议版、期刊版和修订版                    |
| `Asset`             | 按内容 hash 识别的不可变字节内容；文件身份不由路径决定                       |
| `AssetLocation`     | `Asset` 的实际存储位置与状态，可为按账号管理的托管位置或用户磁盘上的链接位置 |
| `Attachment`        | `Edition` 与 `Asset` 的关系及文件角色，例如正文、补充材料或数据附件          |
| `Collection`        | 用户可见的层级目录或由保存查询形成的智能集合                                 |
| `CollectionEntry`   | `Work` 在某个普通目录中的逻辑引用，不复制物理文件                            |
| `Tag`               | 绑定 `Work`、具有稳定 ID 和规范名称的跨目录描述                              |
| `TagAlias`          | 标签的语言变体、缩写、旧名称和近义入口                                       |
| `WorkRelation`      | 两个 `Work` 之间的手工关联，不预先引入证据或观点语义                         |
| `ImportSession`     | 导入箱中一次可取消、可恢复和可对账的导入草稿及处理状态                       |
| `MergeRecord`       | 作品合并历史、原 ID 重定向和可恢复信息                                       |
| `ExternalSourceMap` | Zotero、DOI、arXiv 等外部实体与内部对象的映射及同步游标                      |
| `ResearchProject`   | 毕业论文、课程报告、综述或其他长期研究目标                                   |
| `ReadingContext`    | 一次具有明确目的的阅读上下文，通常关联研究项目或写作主题                     |
| `AnnotationLayer`   | 某个阅读上下文下可独立显示、隐藏和导出的批注集合                             |
| `Annotation`        | 高亮、下划线、区域标注、评论、书签等定位到具体文件版本的标注                 |
| `Evidence`          | 从原文和批注提炼、保留准确出处的证据卡片                                     |
| `Claim`             | 可由多篇论文的证据支持、反驳或限定的研究观点                                 |

### 4.1 身份与关系

- `Work` 可以在没有 PDF 或其他附件时独立存在，不完整元数据也不阻止保存。
- 一个 `Work` 可以拥有多个 `Edition`，并记录一个可由用户修改的首选版本。系统可以建议最新或
  元数据最完整的版本，不自动替换用户选择。
- 一个 `Edition` 可以通过多个 `Attachment` 关联正文、补充材料、数据或其他文件。切片 A 负责
  保存、打开和导出通用附件，只对 PDF 提供内容预览边界。
- `Asset` 表达内容身份，可以被多个 `Attachment` 引用，也可以同时拥有一个托管位置和多个链接位置。
- `Work` 可以属于多个普通目录、关联多个标签，并与其他 `Work` 建立手工相关关系。
- DOI、arXiv ID 等标识符按方案和值规范化后参与重复检测，不设为数据库硬唯一约束。重复标识符
  触发高置信度警告，仍允许保存外部脏数据或人工确认的例外。

### 4.2 两级去重与合并

必须区分：

1. **文件级精确去重**：相同字节得到相同 hash，复用一个 `Asset`，具体磁盘位置由
   `AssetLocation` 表达。
2. **作品级候选重复**：PDF 字节不同，但 DOI 相同或标题、作者、年份高度近似；只提示处理，
   不得自动破坏版本关系。

文件级精确去重采用 SHA-256。`Asset` 同时保存算法名和小写十六进制摘要，托管内容使用
`sha256/<前两位>/<后两位>/<完整摘要>` 寻址；文件名、标题和作者不进入对象路径。

候选重复处理时，用户可以选择关联到现有版本、作为现有作品的新版本、仍新建作品、暂留导入箱或
放弃导入。作品合并保留 `MergeRecord`、原 ID 重定向和外部来源映射，在永久清理前可以撤销。

线性化方式、下载站点或嵌入元数据不同都可能改变 PDF 字节，因此只用 hash 无法识别同一作品。

## 5. 文件与目录模型

### 5.1 一份文件，多处出现

- `Collection` 形成单父节点的层级树；同一父目录下名称不重复，不同父目录下可以同名。
- `Work` 与 `Collection` 是多对多关系。
- 把论文添加到另一个目录只创建 `CollectionEntry`。
- 从一个目录移除论文只删除该引用，不删除 `Work`、`Asset` 或其他目录引用。
- 删除目录只删除目录和其中的逻辑引用，不把作品移入回收站。

### 5.2 文件夹视图

至少需要：

- 左侧目录树、展开状态、当前路径和数量。
- “导入箱、全部文献、未分类、最近阅读、重复项、缺失文件、回收站”等系统视图。
- 面包屑和清晰的多目录归属提示。
- 拖拽时由用户明确选择“移动当前引用”或“添加到另一个目录”，不根据拖拽位置猜测。
- 批量归档、移动、添加标签和检查重复项。
- 结构化保存查询形成用户自建智能目录；系统视图仍由系统维护。
- 文件夹与标签职责分离：文件夹表达主动组织，标签表达跨目录属性。

### 5.3 内容与存储位置

首版通过 `AssetLocation` 同时支持托管文件和外部链接文件：

- **托管文件**：默认复制到按账号管理的内容寻址附件库；相同 hash 只保存一份物理文件，便于
  去重、校验、备份和跨设备恢复。
- **链接文件**：保留用户现有磁盘位置，适合已有大量手工目录的用户。
- 一个 `Asset` 在同一账号中最多拥有一个托管位置，可以同时保留多个链接位置。
- 不同账号之间不共享物理去重、托管路径或引用计数。
- 托管附件库使用默认账号目录，也允许用户修改到其他本机固定磁盘位置。迁移必须完成复制、hash 校验、
  切换和失败回滚，不要求用户手工搬移。A1 不把移动磁盘、网络盘或云盘目录作为托管附件库。
- 界面目录是逻辑分类，不要求映射为真实磁盘目录。
- 链接位置同时记录用户选择的原始路径和当时 `realpath` 得到的解析路径。用于实际 I/O 的路径不得先转小写或
  改写 Unicode 形式；大小写折叠与 Unicode 规范化只用于界面候选提示，不作为数据库唯一约束。
- `stat` 提供的设备与文件标识只用于同一次运行中的位置核对，不能替代内容 hash，也不能证明两个路径长期
  指向同一文件。硬链接、符号链接和大小写不敏感文件系统都可能让规范路径不是唯一身份。
- 符号链接、移动磁盘、网络盘和云盘目录可以作为链接来源；断开或不可用时进入缺失状态，首版不承诺持续
  文件监听或网络盘一致性。
- 重新定位支持单文件选择和批量根目录映射。hash 相同时恢复原位置；hash 不同时把所选文件作为
  新 `Asset` 候选，不静默替换原内容。
- 链接文件在原路径发生内容变化时标记为已变更，保留原 `Asset` 记录并让用户确认新内容属于哪个版本。
- “转为托管”和“导出到真实目录”始终先复制再校验。成功后保留原文件，删除某个位置索引由用户
  另行操作。

### 5.4 移除、回收与恢复

界面和服务层明确区分四种操作：

1. **从目录移除**：只删除 `CollectionEntry`。
2. **移除附件**：只解除 `Attachment` 关系；若托管 `Asset` 已无任何附件或导出任务引用，其托管位置进入
   附件回收状态。
3. **将作品移入回收站**：隐藏整个 `Work` 及其版本、附件关系和目录关系，但保留恢复信息。
4. **永久删除**：显示受影响对象，重新检查引用计数，再清理数据库关系和无引用托管文件。

首版回收站不自动过期清理。链接位置在任何删除流程中都不删除用户磁盘上的原文件。恢复作品时一并恢复
可用的关系；若附件已缺失或被永久清理，恢复作品同时显示缺失状态，不把部分恢复报告为完整成功。

### 5.5 文件与数据库一致性

托管导入先进入解析后托管根目录内的临时区，完成流式 SHA-256、复制和校验后再原子切换到内容寻址位置。
临时区与最终对象必须确认处于同一设备；不依赖跨设备 `rename`。若最终 hash 路径已经存在，则校验已有文件并
复用，不用覆盖式 `rename` 替换它。数据库只在文件可用且校验通过后才将托管位置标记为可用。链接导入在正式
入库前完成当次可读性和 hash 校验。

文件占用、只读、权限不足、空间不足和跨设备错误分别保留机器可读原因。Windows 上的打开文件可能因共享模式
拒绝移动或删除，服务层把 `EBUSY`、`EPERM`、`EACCES` 作为可重试或等待用户处理的文件状态，不假设 POSIX
式“删除后打开句柄仍可读”。

`ImportSession` 保留导入阶段和失败原因。取消、超时或崩溃后的对账需覆盖：

- 临时文件已存在但尚未提交：恢复导入或安全清理。
- 内容文件已就位但数据库未提交：按 hash 识别孤立文件并补提交或清理。
- 数据库声称位置可用但文件不存在或校验失败：转为缺失或已变更状态，不静默掩盖。

未完成的导入不作为正式 `Work` 出现在文献库中。

## 6. 阅读上下文与批注图层

### 6.1 目标行为

同一个 `Asset` 在多个目录或研究项目中仍只有一份文件，但可以拥有互不干扰的批注图层。
用户可以选择只看当前图层，也可以叠加查看其他图层。

### 6.2 图层模型

采用“通用批注层 + 多个命名上下文层”：

- 通用层记录与具体项目无关的核心理解。
- 研究项目层记录服务于毕业论文、课程报告或综述的批注。
- 文件夹或项目可以绑定默认图层，但移动目录不能改变批注所有权。
- 阅读器必须始终明显显示当前写入图层，避免批注被写进错误上下文后难以发现。

不推荐把批注严格绑定 `CollectionEntry`。目录重组后批注的研究含义不应随之漂移。

### 6.3 批注定位与版本

- 批注绑定具体 `Asset` 或 `Edition` 版本。
- 定位信息至少保留页码、页面坐标、文本引用和文本上下文指纹。
- PDF 版本变化后不得静默套用旧坐标；可以尝试迁移，但必须展示未匹配项。
- 批注、评论、证据卡片和导出副本之间需要可追溯关系。

## 7. 标签系统

### 7.1 标签不是小色块集合

首版标签系统拥有独立管理页，并覆盖：

- 普通标签绑定 `Work`；版本特有信息保留在 `Edition` 元数据中。
- 规范名称、别名、说明、使用次数和最近使用时间。
- 规范化去除首尾空格并统一 Unicode 形式。大小写、语言、单复数及近似名称只用于重复建议，
  不静默合并用户的可见名称。
- 支持重命名、合并和删除，并在执行前展示受影响论文；合并后旧名称保留为别名。
- 标签删除提供短期撤销，永久删除标签也不删除任何 `Work`。
- 颜色只作为辅助辨识，不作为标签的主要信息结构。

### 7.2 找回体验

- 模糊匹配规范名称和别名。
- 展示最近使用、常用和当前项目使用过的标签。
- 相似标签同时展示说明和代表论文，帮助辨别差异。
- AI 可以推荐已有标签，但默认不得未经确认批量创建新标签。

自动聚类、自动批量整理和复杂标签组合明确后置，不作为首版验收条件。

## 8. 元数据与引用

### 8.1 宽松内部模型

- `Work` 允许没有附件；手工建立的元数据记录、网页、标准和其他研究材料在切片 A2 中可直接保存。
- 类型必须允许 `unknown`、`other` 和用户自定义值。
- 标题、作者、日期、期刊、会议、卷期页码等字段均允许缺失。
- 作者使用可扩展角色，而不是只有固定的作者和编辑。
- 日期可以分别表达发表、上线、接收、修订和访问时间。
- 支持 DOI、ISBN、ISSN、arXiv ID、PMID、URL 等多个标识符。
- 无法映射的外部字段必须保存在原始记录中，不能静默丢失。

### 8.2 字段级来源与冲突

每个关键字段应能够记录来源、获取时间和是否人工确认。多个来源冲突时逐字段比较，不能用
“整条记录覆盖”抹掉人工修正。

默认建议优先级为：

```text
人工确认
  → 精确标识符匹配的外部来源
  → 其他外部来源
  → PDF 内嵌元数据
  → 正文首页识别
  → 文件名
```

优先级只决定默认建议，不代替字段级冲突展示。系统保存必要的外部原始记录、来源、获取时间和解析版本，
不保存凭据或无关响应头。

### 8.3 引用格式是输出层

内部模型不绑定某一种 BibTeX entry type 或 CSL item type。引用导出时再映射到目标格式，
并对无法准确表达的字段给出提示。不得为了兼容引用格式而阻止用户保存不完整材料。

### 8.4 首版导入与识别范围

切片 A1 面向用户已经下载到本地的 PDF，不包含浏览器 Connector 或网页内直接抓取。导入时依次利用 PDF
嵌入元数据、正文首页文本、文件名以及 DOI、arXiv ID 等可识别标识符生成元数据建议，并在正式入库前
允许用户确认和修正。

切片 A2 增加无附件 `Work` 和手工元数据记录；BibTeX、RIS、CSL JSON 的具体格式适配仍属于切片 D。

无法可靠识别的信息保持缺失并保留原始内容，不为了补齐字段而编造结果。扫描型或无可靠文本层的 PDF 仍可以
使用文件名、内嵌属性和人工输入入库，并标记正文文本不可用；OCR 属于切片 B。

首次启用外部元数据查询时，界面说明将访问的服务以及会发送的 DOI、标题等信息。默认不上传整份 PDF。离线、
超时或外部服务失败不阻止入库；系统保留未完成查询状态，支持用户手动重试和有上限的后台重试。

已入库元数据不自动定期刷新。用户主动刷新时，新结果仍作为字段级建议，不覆盖已人工确认的值。具体外部
元数据提供方、调用优先级、速率限制和许可条件按以下 A1 选型执行：

1. 本地先用 `pdfjs-dist@6.2.108` 的 Node legacy build 读取 PDF 内嵌信息和正文第一页，只做识别，
   不在 A1 引入阅读器、渲染或 OCR。解析放入可强制终止的隔离任务，关闭脚本求值，限制输入、页数、运行时间
   和返回文本；扫描型、损坏或超时只表示本地识别不可用，不阻止导入。
2. 识别到 arXiv ID 时查询 arXiv API。Atom XML 使用 `fast-xml-parser@5.11.0` 解析并关闭实体处理，
   不用正则表达式解析 XML。
3. 识别到 DOI 时先规范化 DOI，再用 Crossref agency 判断登记机构；Crossref 与 DataCite 的 DOI 分别向对应
   精确接口查询。OpenAlex 的 DOI 精确查询只作为补充候选，不覆盖登记机构结果。
4. 没有可靠标识符时，使用 OpenAlex 的标题、作者、年份检索生成候选，必要时补充 Crossref bibliographic
   候选。标题搜索结果必须在本地按标题、作者和年份重新排序，只供用户选择，不能自动确认作品或版本。
5. A1 不默认接入 Semantic Scholar；其许可条件与当前个人、非商业研究范围绑定，不适合作为基础元数据依赖。

外部查询只发送 DOI、arXiv ID 或必要的标题、作者、年份，不上传 PDF。默认单客户端上限为 Crossref 每秒
4 次且并发 1、DataCite 每秒 1 次、arXiv 每 3 秒 1 次、OpenAlex 每秒 2 次，并继续遵守服务端返回的更严格
限制。单请求默认 8 秒超时，网络错误、`429` 和 `5xx` 最多重试 2 次并遵守 `Retry-After`；普通 `4xx`
不重试。精确标识符的成功结果作为来源记录持久保存，未找到结果缓存 24 小时，瞬时失败缓存 5 分钟。
导入流程不等待后台重试完成。

## 9. PDF 阅读器能力底线

第一版可称为“阅读器”之前，至少应覆盖：

- 文档大纲、缩略图、页码跳转、缩放和常用页面布局。
- 全文搜索、文本选择和复制。
- 高亮、下划线、区域标注、评论和书签。
- 批注列表定位、图层切换及当前图层提示。
- 多标签页、最近阅读、阅读位置和缩放状态恢复。
- 单页、连续滚动和双页阅读，以及夜间阅读模式。
- 键盘快捷键和基本无障碍操作。
- 原始文件打开、文件位置查看和带批注副本导出。

手写和触控能力后置评估，不能仅从视觉原型推导。

## 10. 阅读器性能约束

### 10.1 运行策略

- 只渲染视口附近页面，离开缓存窗口的 Canvas 和文本层可回收。
- 后台标签页进入休眠，只保留文档句柄和可序列化阅读状态。
- 页面渲染、解析和索引使用可取消的后台任务，切换文档后停止无用工作。
- 缩略图、正文页面、文本层和搜索索引分别按需加载。
- 使用有明确上限的 LRU 缓存，不随打开文档数量无限增长。
- 大型 PDF 使用安全模式，避免打开时一次性解析、渲染和索引全文。
- 文本型 PDF 自动建立全文索引，但索引任务只在后台执行、可以暂停或取消，不能阻塞当前页面。
- 检测到扫描型或缺少可靠文本层的 PDF 时明确提示用户；用户确认后才进入 OCR 流程。
- OCR 通过可替换的引擎接口执行，不在领域模型中绑定具体模型。首版发布前至少完成一个 OCR
  引擎的独立技术验证，再决定默认实现；OCR 结果经校验后进入全文索引。

### 10.2 实施前必须建立的基准

在选定 PDF 引擎和运行形态前，准备小型、扫描型、图片密集型、超长和损坏边缘文档，测量：

- 首次可见页面时间。
- 连续翻页与快速跳页的 CPU 峰值。
- 单文档和多文档峰值内存。
- 后台标签页休眠后的保留内存。
- 关闭文档后的内存回收。
- 全文搜索和索引建立时间。
- OCR 的语言覆盖、准确性、CPU 与内存开销，以及中断后的恢复行为。

具体预算数值需基于目标设备与样本文档确定，本文档不提前编造阈值。

## 11. 从阅读到研究知识

### 11.1 导入箱与筛选

每次文件导入都先建立 `ImportSession` 草稿并进入导入箱。单篇导入可以在同一流程中立即确认，批量导入
支持按重复组和问题类型逐组处理。

```text
导入
  → 建立草稿并进入临时区
  → 计算 hash 并检查文件与作品重复项
  → 本地识别与外部元数据查询
  → 确认存储模式、作品归属与元数据
  → 选择目录和已有标签
  → 正式入库
```

作品级候选重复允许用户关联到现有版本、建立新版本、仍创建新作品、暂留导入箱或放弃导入。取消导入时
清理未提交的临时文件；中断后按 §5.5 对账。未确认内容不作为正式 `Work` 进入文献库、目录和标签体系。
研究项目关联在对应上层能力存在时可选显示，不成为切片 A 入库的必要条件。

### 11.2 证据链

首版必须完成以下闭环，而不是只预留数据表：

```text
原文定位
  → 批注
  → 证据卡片
  → 支持 / 反驳 / 限定观点
  → 跨论文对照矩阵
  → 综述或写作材料
```

证据必须保留作品、文件版本、页码、原文、批注图层和提取时间。写作材料应能返回准确出处，
不能退化为与来源脱离的普通文本片段。观点需要能够聚合多篇论文中的支持、反驳和限定证据，
跨论文对照后仍能逐项回到对应原文。

### 11.3 论文项目工作流

可以在 Research Workbench 上层提供研究项目、阶段、里程碑、文献矩阵、方法模型、导师意见和
文稿版本管理。这些是候选能力，不绑定现有视觉原型的布局或固定八阶段流程。

只有“阅读这篇论文”“核实这条证据”“完成综述初稿”等可执行动作才投影为 core `Item`，
论文本身、批注和观点不属于通用待办。

## 12. 检索与重访

### 12.1 切片 A 的结构化检索

可信文献库完成时，搜索和筛选至少覆盖：

- 标题、作者、年份、期刊、标识符和自定义字段。
- 目录、标签、附件角色、文件模式和文件状态。
- 缺失字段、重复项、缺失文件和未完成元数据查询等维护条件。
- 手工建立的相关文献关系。

结构化查询可以保存为智能目录。普通目录保存用户显式添加的 `CollectionEntry`，智能目录保存查询条件，
两者不混用。

### 12.2 后续检索边界

PDF 正文、批注和阅读状态随切片 B 进入检索；笔记、证据和观点随切片 C 进入检索。结构化筛选、模糊搜索和保存
查询应先于语义搜索可靠完成。语义检索可以补充“记得内容但忘了标题”的场景，不成为基础检索的补偿。

## 13. Zotero 优秀能力与互操作边界

### 13.1 不能丢失的基线能力

- 多级集合，以及一篇论文属于多个集合。
- 附件管理、缺失文件提示和重复项识别。
- DOI、ISBN、arXiv 等标识符辅助获取元数据。
- 安全的重复文献合并。
- 全文搜索、保存查询、标签、关联论文、笔记和批注。
- BibTeX、RIS、CSL JSON 等常见格式导入导出。
- 引用复制和基础参考文献生成。

“不能丢失”指产品能力和用户结果，不要求复制 Zotero 的界面、内部数据库结构或全部插件生态。

### 13.2 分阶段互操作

切片 A 负责定义不丢字段的内部导入导出模型、原始记录保存规则、附件清单和可迁移导出包。切片 D 负责把这个
内部模型映射到 BibTeX、RIS、CSL JSON 等具体格式。首版只实现基础互操作；Zotero 专用迁移及后续同步只保留
可扩展接口，不进入首版范围：

1. **首版基础互操作**：BibTeX、RIS、CSL JSON 导入导出，保留外部 key 和原始记录。
2. **后续 Zotero 迁移**：导入条目、集合、标签、附件映射和能够可靠转换的批注。
3. **后续增量互操作**：根据真实需求评估外部 ID、游标和冲突处理。
4. **远期双向同步**：只有删除、版本、附件和批注冲突语义全部确定后才考虑。

不得把直接修改 Zotero 数据库作为基础方案。Connector、Word 插件和完整团队库不属于首轮目标，
但导出接口不能堵死未来接入。

## 14. 存储、备份与同步边界

- PDF 不作为 SQLite BLOB 保存；数据库只保存文件标识、路径、hash、大小、MIME、版本和状态。
- 当前账号数据库备份可以覆盖研究元数据、阅读状态和旁挂批注，但不会自动携带 PDF 附件。
- 备份和恢复界面明确区分“数据库备份”与“完整资料导出”，不用笼统的“备份成功”掩盖附件未包含。
- 切片 A2 的可迁移导出包包含规范 JSON、元数据、目录、标签、作品关系、来源记录和附件清单。用户可选把托管文件
  复制进导出包。
- 链接文件默认只输出位置和状态清单并报告缺失项；只有用户明确选择时，才复制当前可访问的链接文件。
- 附件备份、去重上传、恢复校验、配额和可选加密需要单独设计。
- 数据库恢复与附件恢复必须检测缺失和版本不一致，不能显示“恢复成功”却留下静默断链。
- 当前云端“保险箱”模型不等于多设备并发同步；研究模块不得暗中假设实时协作成立。

## 15. 仓库边界

Research Workbench 应作为独立领域进入 `modules/research`，遵守现有模块边界：

- 模块只能依赖 core，模块之间零依赖。
- core 不感知论文、PDF、Zotero、批注或研究项目。
- 模块拥有自己的迁移、存储适配器、契约、服务端注册和 UI 注册。
- 与应用壳层的前后端交接继续通过模块 `contract.ts` 和注册点完成。
- Todo、工作台与日历不直接依赖 research；research 只把可执行动作投影为 core `Item`。

可能的内部目录如下，仅表达职责，不是实施文件清单：

```text
modules/research
├─ library       作品、版本、集合和标签
├─ storage       文件索引、去重、回收站和附件状态
├─ ingest        导入箱、元数据识别和重复检测
├─ reader        PDF 阅读状态与性能策略
├─ annotation    批注图层、书签和笔记
├─ knowledge     证据、观点和综述矩阵
└─ interop       Zotero、BibTeX、RIS、CSL JSON
```

A1 的 PDF 识别与外部元数据客户端先保留在 research 模块内部，通过窄接口隔离解析任务和远程提供方。
只有切片 B 的阅读器或其他模块出现真实复用需求时再提取独立 package。

### 15.1 内置 AI Runtime 与 Harness 接入预留

未来的 Harness 类能力计划作为 Personal WorkBench 内置的 AI Runtime 运行，而不是以一个外部
系统直接控制 Research Workbench。Research Workbench 的核心管理、检索和阅读能力仍不能依赖
AI 服务才能运行。

- 内置 AI Runtime 属于应用级基础能力，负责模型调用、会话与任务生命周期、流式输出、取消、
  能力编排、用户确认、凭据和审计；它不成为 research 领域数据的真源。
- `modules/research/src/contract.ts` 应提供稳定、版本化、可结构化验证的领域能力与数据契约，
  由应用装配层注册给内置 Runtime。不能因此让 research 依赖其他业务模块，也不能让 core 感知
  论文或 AI 领域。
- research 模块仍负责领域输入验证、权限判断和持久化语义；Runtime 只能通过已注册能力操作数据，
  不能绕过模块服务直接读写数据库。
- Runtime 设计时兼顾结构化请求与结果、流式增量、可取消任务、工具或能力调用、机器可读错误、
  请求关联以及来源追踪等常见接口形态。
- **MCP 作为首选兼容目标**：内部能力注册应能自然映射为 MCP 的 tools、resources 等概念，
  首个通用接入适配器优先考虑 MCP；但同进程模块之间不必为了兼容而强制经过 MCP 传输。
- Anthropic Messages API、OpenAI Responses API 等属于模型供应商适配层，可以按实际使用的模型
  分别支持，不作为 WorkBench 的固定内部 API 格式。具体字段在 Runtime 项目需求明确后再确定。
- 模型接入优先兼容 CC Switch 管理的配置，同时支持用户直接配置自己的 API Key（BYOK）；具体
  集成方式留待 Runtime 设计时确定。
- 接口优先传递 `Work`、`Edition`、`Asset`、`ReadingContext` 等稳定资源标识，不直接暴露内部
  数据库结构、任意磁盘路径或默认传输整份 PDF。
- AI 生成的标签、元数据、证据和观点默认属于待确认建议；是否持久化以及如何覆盖既有内容仍由
  WorkBench 的权限、验证和确认流程决定。
- 凭据、隐私边界、远程发送范围和生成结果来源必须可审计，不能把模型密钥或供应商响应对象
  混入研究领域数据模型。

本节只保留未来兼容方向，不要求在当前阶段确定完整 API schema，也不阻塞任何非 AI 切片。

## 16. 已确认的产品切片与首版范围

以下仅用于约束依赖顺序，不是 implementation plan。每个切片拥有自己的开工门槛；后续切片的
未决问题不能反向阻塞已经具备独立闭环的前置切片。

首版产品范围包含切片 A、B、C，并按 A → B → C 的顺序形成可验证闭环。切片 D 在首版只完成
BibTeX、RIS、CSL JSON 基础互操作以及未来扩展所需的接口边界。

A、B、C、D 是产品能力切片。由于切片 A 内部包含多组复杂且高风险语义，它被拆成两个可独立验收的子里程碑：
A1 和 A2。它们不与 A、B、C 平级，共同完成切片 A。

正式实现 A1 之前先确认完整切片 A 的领域身份、数据归属、文件生命周期、后续管理能力和迁移出口，
避免 A2 反过来要求 A1 迁移核心数据。实施顺序仍为 A1 → A2；A2 的逐文件实施计划在 A1 闭环验证后再编写。

### 切片 A：可信文献库

完成作品、版本、文件、目录、标签、导入箱、元数据来源和可迁移导出，先证明不会丢文件和字段。

切片 A 采用托管与链接并存的文件模式以及安全删除与恢复语义，不依赖完整 PDF 阅读器引擎和
阅读性能验证即可先行实施；A1 仍需支持用于元数据识别的基础 PDF 文本与内嵌信息提取。
PDF 识别与外部元数据提供方采用 §8.4 的已验证选型。

#### A1：论文导入与安全存储闭环

A1 先证明论文从本地 PDF 进入 WorkBench 后，能够被稳定识别、去重、分类、检查并安全恢复。
第一个用户可验收闭环是：

```text
导入本地 PDF
  → 选择托管或链接
  → 计算内容 hash
  → 本地自动元数据识别与外部元数据查询
  → 用户确认或修正元数据
  → 创建或复用 Work / Edition / Asset / Attachment
  → 在最小文献库中显示
  → 添加到多个目录
  → 安全移除、缺失检测、重新定位与恢复
```

A1 当前已确认的范围是：

- 建立 `Work`、`Edition`、`Asset`、`AssetLocation`、`Attachment`、`Collection`、`CollectionEntry`、
  `ImportSession` 和 `MergeRecord` 的最小稳定身份与关系。
- 同时支持托管和链接位置，保留内容 hash、大小、MIME、已知路径、位置模式和状态。
- 对 PDF 内嵌元数据、正文首页、文件名和可识别标识符进行本地自动识别，并通过外部元数据服务生成
  补全或冲突建议；所有建议均在正式入库前交由用户确认。
- 保留字段来源、获取时间和人工确认状态；外部结果不得静默覆盖用户已确认的值。
- 按 hash 对 `Asset` 精确去重。已经存在且作品归属明确的同一文件再次导入时，复用现有对象并只增加
  需要的 `CollectionEntry`，不静默新建一套 `Work / Edition / Attachment`；归属不明时交由用户确认。
- 对 hash 不同但 DOI 相同或标题、作者、年份高度近似的文件只提示作品级候选重复，不自动合并或
  丢弃版本。
- 提供最小 UI：导入 PDF、选择存储模式、确认元数据、查看文献库、多目录归属和文件状态。
- 通过自动测试覆盖精确重复、候选重复、目录引用、托管与链接删除、缺失、重新定位、回收、恢复和中断对账。

A1 不包含 PDF 阅读器、OCR、AI、批注、证据链、完整标签治理和完整引用格式导入导出，只为它们保留
稳定资源 ID 与模块契约边界。

#### A2：完整文献库治理与迁移出口

A2 在 A1 的可信身份和文件基础上完成切片 A 的其余能力：

- 完整导入箱和批量筛选，包括按重复组、缺失字段和失败原因处理。
- 无附件 `Work`、手工元数据记录、通用附件角色和手工相关文献关系。
- 完整层级目录、多目录归属、批量操作、系统视图和保存查询形成的智能目录。
- 标签管理页、规范名称、别名、近似检测、重命名、合并、删除和撤销。
- 覆盖元数据、目录、标签、文件与维护状态的结构化搜索、模糊搜索和保存查询。
- 规范 JSON、原始来源记录、附件清单和可选附件文件组成的可迁移导出包。
- 导入箱、全部文献、目录、标签、重复项、缺失文件和回收站的完整管理界面。

A2 不实现 PDF 正文搜索、批注、OCR、证据链或具体引用格式适配器。PDF 正文与批注属于 B/C，BibTeX、RIS、
CSL JSON 适配属于 D。

### 切片 B：可长期使用的阅读器

完成基本阅读、阅读状态、批注图层和大型文档性能基准，证明连续使用不会失控占用资源。

切片 B 已确定采用通用层 + 命名上下文层、浏览器 + 本地 server 以及 §9 的首版阅读能力。进入
实施计划前仍需准备测试语料，完成 PDF 与 OCR 引擎技术验证并据此确定性能预算。

### 切片 C：研究知识闭环

完整实现批注、证据、观点、跨论文对照和来源回跳，让阅读结果能够进入综述与写作。这里的
“完整”指 §11.2 的研究知识闭环，不要求同时实现 §11.3 中全部候选项目管理能力。

### 切片 D：生态兼容与附件保护

首版实现 BibTeX、RIS、CSL JSON 基础导入导出并保留版本化扩展接口，不实现完整 Zotero 迁移、附件云备份
或双向同步；后续是否实现由真实迁移与恢复需求决定。

## 17. 关键验收场景与测试策略

在为某个子里程碑或切片编写实施计划前，先把属于它的场景改写为可直接转成自动测试或手动验收的标准。

### 17.1 切片 A 功能验收

1. 同一 PDF 以托管模式导入两次，只保留一个 `Asset` 和一份托管内容；重复导入可增加新目录引用。
2. 同一 `Asset` 可以同时保留托管位置和多个链接位置；不同账号之间不共享物理文件或引用计数。
3. 两份字节不同但 DOI 相同或元数据高度近似的 PDF 进入候选重复；用户可选现有版本、新版本、
   新作品、暂留或放弃，系统不自动合并。
4. `unknown` 类型、不完整元数据、无附件 `Work` 和扫描型 PDF 都可以保存、搜索、编辑和无损导出。
5. 外部元数据服务离线或失败时仍可入库；恢复后可重试；新结果不覆盖人工确认字段，原始来源可追溯。
6. 取消或中断导入不会在文献库留下半成品 `Work`；重启对账能处理临时文件、孤立托管内容和断链记录。
7. 链接文件移动后标记为缺失。重新定位到同 hash 文件时恢复；所选文件 hash 不同时进入新 `Asset`
   候选，不替换原内容。
8. 删除一个目录或一个 `CollectionEntry` 不会删除其他目录中的作品、附件关系或物理文件。
9. 移除目录引用、移除附件、回收作品和永久删除是四个独立操作；无引用托管文件经回收与二次检查后才清理，
   链接原文件永不由 WorkBench 删除。
10. 恢复作品时恢复仍可用的关系；附件缺失时明确报告部分恢复。回收站不自动清空。
11. 作品合并保留原 ID 重定向、来源映射和可撤销记录；永久清理前可以恢复。
12. 近似标签只提示不自动合并；标签合并保留旧名为别名，标签删除和撤销不丢失作品。
13. 结构化检索覆盖元数据、目录、标签、文件状态和维护条件；保存查询可作为智能目录重复执行。
14. 可迁移导出包可还原元数据、目录、标签、作品关系、来源和附件清单；托管与链接文件按用户选项复制，
    缺失项单独报告。
15. 托管附件库迁移只在复制和 hash 校验完成后切换；中断时继续使用原位置并可重试。

### 17.2 切片 A 规模与资源测试

切片 A 的基线资料库规模为 10,000 个 `Work`、20,000 个 `Asset` 索引、1,000 个标签和单次 200 个文件的
批量导入。数量规模与真实 PDF 容量分层验证，不为了测试记录数量复制等量大型 PDF。

| 测试层       | 方法                                                             | 默认资源边界           |
| ------------ | ---------------------------------------------------------------- | ---------------------- |
| 数据规模     | 临时磁盘 SQLite 直接生成领域记录，测试索引、分页、搜索和批量操作 | 不生成等量 PDF         |
| 文件生命周期 | 30–50 个小型真实 PDF，覆盖去重、链接、缺失、回收、恢复和中断     | 进入默认测试套件       |
| 批量导入     | 200 个小型生成文件，验证流程数量、候选分组、取消和失败恢复       | 进入专项测试           |
| 大文件行为   | 单个约 256 MiB 生成文件，验证流式 hash、复制进度、取消和清理     | opt-in，不进入每次提交 |

默认测试套件的临时磁盘占用上限为 250 MiB，用例结束后清理独立临时目录。数据规模测试使用临时磁盘数据库，
不用 `:memory:` 代替需要观察的真实 SQLite 索引、查询和 WAL 行为。磁盘不足通过可控文件系统边界注入错误，不实际写满磁盘。

20,000 个真实目录项的文件库审计和更大文件测试作为手动或夜间任务，并允许通过配置把临时根目录指向外接磁盘。

首次 SQLite 原型基准已给出以下 A1 验收阈值。查询阈值不包含 PDF 解析、文件复制、hash 和网络等待；正式表结构、
索引和 Repository 完成后使用相同数据分布重跑，不能用原型结果代替实现验收。

| 指标                                          | A1 验收阈值               |
| --------------------------------------------- | ------------------------- |
| 普通列表、分页、精确筛选和元数据搜索 p95      | 不超过 100 ms             |
| 缺失审计、重复分组和导入对账查询 p95          | 不超过 250 ms             |
| 200 条纯元数据在单事务中的提交时间            | 不超过 1 s                |
| 1,000 次精确内容 hash 查询                    | 总计不超过 100 ms         |
| 10,000 `Work` / 20,000 `Asset` 索引数据库大小 | 不超过 100 MiB            |
| 上述基准进程峰值 RSS                          | 不超过 250 MiB            |
| 同规模数据库 `integrity_check`                | 不超过 2 s                |
| 默认自动测试的全部临时磁盘占用                | 不超过 250 MiB 且结束清理 |

### 17.4 A1 技术验证记录

2026-08-23 在 macOS APFS、Node.js 22.22.1 和仓库现有 SQLite 栈上完成首轮验证：

| 验证项             | 实测结果与结论                                                                                                                                                                                                                                                    |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SHA-256 与托管复制 | 256 MiB 生成文件两次流式 hash 分别约 1.26 s 和 1.38 s，吞吐约 203 MiB/s；流式复制约 1.42 s，目标 hash 一致。约 16 MiB 时取消返回 `ABORT_ERR`，残留临时文件可清理。采用 Node 内置 `crypto`，不增加 BLAKE3 依赖。                                                   |
| PDF 基础识别       | `pdfjs-dist@6.2.108` legacy build 可从带内嵌字段 PDF 和论文样本提取标题、作者、关键词、首页文本、DOI 与 arXiv ID；扫描型返回无文本，截断文件返回明确的无效 PDF 错误。现代 Node build 在无 DOM 环境缺少 `DOMMatrix`，A1 不使用它。                                 |
| arXiv XML          | `fast-xml-parser@5.11.0` 在 Node.js 22 下成功解析官方 Atom 响应；关闭实体处理后，自定义实体保持未展开。该依赖为 MIT，安装体积约 1.3 MiB。                                                                                                                         |
| 外部元数据         | Crossref、DataCite、arXiv 和 OpenAlex 的精确标识符查询均返回有效记录。标题检索出现同名后发论文，Mozilla 样本还出现会议版与期刊载体两个有效 DOI，确认标题检索只能生成候选，`Work / Edition` 不能合并。                                                             |
| SQLite 目标规模    | 10,000 `Work`、20,000 `Edition / Asset / Location / Attachment`、20,000 目录引用、1,000 标签和 30,000 作品标签在约 0.53 s 内生成；数据库约 24.97 MiB，峰值 RSS 约 77.3 MiB，`integrity_check` 约 127 ms。普通查询 p95 为 0.02–4.62 ms，200 条事务提交约 2.11 ms。 |
| macOS 文件语义     | 原始 Unicode 路径可保留；当前 APFS 同时接受 NFD 别名和大小写不同别名。符号链接目标移动后读取与 `realpath` 均为 `ENOENT`，硬链接共享设备与 inode。只读覆盖为 `EACCES`；打开文件仍可移动、删除并由原句柄继续读取；同路径 `rename` 会替换目标。                      |
| Windows 路径语法   | Node `path.win32` 已覆盖盘符、UNC、长路径命名空间和跨盘相对路径，但这不等同于 Windows 文件系统实测。验证入口为 `scripts/research-windows-file-semantics.mjs`；符号链接权限、文件占用、只读、大小写、长路径和原子提交仍需在真实 runner 上完成。                    |

文件语义验证模块的当前实测状态：

| 平台    | 状态     | 已知环境与结论                                                  |
| ------- | -------- | --------------------------------------------------------------- |
| macOS   | 已实测   | 2026-08-23；Darwin 24.6.0、arm64、APFS、Node.js 22.22.1，已通过 |
| Windows | 尚未实测 | 已准备下述脚本和指令，实际系统、架构与文件系统待运行时记录      |
| Linux   | 尚未实测 | 当前是兼容目标，尚未声明通过                                    |

首轮测试使用临时目录，已验证业务样本可以在 250 MiB 临时空间预算内分层执行；不需要在本机复制 10,000 或
20,000 份真实 PDF。

A1 可以照常进入实施计划和开发。当前文件语义验证模块已在 macOS 实测，Windows 结果保留为待测，不阻塞
数据库、领域模型、元数据、API 或 UI 等其他模块。以后修改路径、文件占用、移动、删除或原子提交逻辑时，同步
维护该兼容性脚本；若同一模块先在 Windows 验证，则反向补测 macOS。

Windows 本地 NTFS 使用 Node.js 22.22.1 或更高版本运行：

```powershell
node .\scripts\research-windows-file-semantics.mjs
```

需要验证移动盘、网络共享或云盘同步目录时，将测试根目录指向对应位置：

```powershell
node .\scripts\research-windows-file-semantics.mjs --root "D:\research-validation"
node .\scripts\research-windows-file-semantics.mjs --root "\\server\share\research-validation"
```

脚本输出 JSON 结果；断言全部通过时退出码为 `0`，失败时为 `1`。所有样本创建在独立临时目录中，执行结束后
自动清理。

### 17.5 后续切片关键场景

1. **切片 B**：同一 PDF 在两个阅读上下文中拥有独立批注并可叠加显示；多个后台 PDF 休眠和关闭后回收渲染资源。
2. **切片 B**：大型 PDF 打开时不同时执行全文渲染、索引和 OCR；扫描型 PDF 提示后才进入可取消、可恢复的 OCR。
3. **切片 C**：证据卡片可以回到准确作品、版本、文件、页码和原文位置。
4. **切片 D**：BibTeX、RIS、CSL JSON 可导入和导出，无法映射的原始字段不静默丢失。
5. **整体**：即使不使用 Zotero，全部核心功能仍然成立；离开 WorkBench 时仍有明确的数据导出路径。

## 18. 明确暂缓或不做

- 不把视觉原型当作固定页面设计或阶段模型。
- 不以复刻 Zotero UI、数据库结构或全部插件为目标。
- 不在首版实现 Zotero 专用迁移、双向同步、Word 插件或团队协作库。
- 不在首版实现浏览器 Connector 或论文网页内直接抓取。
- 不在当前阶段引入桌面外壳；未来转 App 时重新进行完整设计。
- 不在首版实现标签自动聚类、自动批量整理或复杂标签组合。
- 不自动合并作品级候选重复，不自动定期覆盖元数据。
- 不自动清空回收站，不通过 WorkBench 删除链接位置的磁盘原文件。
- 不从第一天自研完整 CSL 引擎，优先采用成熟实现并保持输出适配层。
- 不默认把批注直接写回原 PDF。
- 不让 AI 未经确认自动创建大量标签、修改元数据或合并论文。
- 不让核心管理与阅读流程依赖内置 AI Runtime 或远程模型才能运行。
- 不在具体接入项目和需求尚未明确时锁定某一种 AI 供应商或 Agent 协议。
- 不把实时多端协作、CRDT 或服务端常驻部署夹带进本模块。
- 不在设计未确认时创建详细 implementation plan 或数据库迁移。

## 19. 尚未决定的问题

产品大方向和完整切片 A 的产品语义已经确认。以下是首轮技术验证后仍需完成的事项：

1. **跨平台交付**：Windows、macOS 的安装和本地 server 启动方式，以及 Linux 兼容目标的明确
   支持边界。
2. **Windows 兼容性实测**：方便使用 Windows 环境时按 §17.4 的指令验证 NTFS 大小写与 Unicode 路径、
   符号链接权限、只读文件、打开文件的移动与删除、长路径、盘符与 UNC，以及同一托管根目录内的原子提交。
   当前状态为文件语义模块尚未在 Windows 实测；它不阻塞其他 A1 模块。在把文件语义模块标记为 Windows 兼容
   前完成；若该模块以后先在 Windows 发生实现变更，则反向补测 macOS。
3. **非固定磁盘场景**：在声明相应位置受支持前补测移动磁盘重连、网络盘中断和至少一种云盘占位文件；这些
   位置作为链接来源，不扩大为 A1 托管库。
4. **切片 B**：用哪些真实文档构成性能基准，目标设备、内存预算和验收阈值是什么。
5. **切片 B**：PDF 与 OCR 引擎候选的语言覆盖、准确性、性能、许可证和跨平台表现。
6. **切片 C**：跨论文对照矩阵的最小交互和导出形式，以及证据与观点的编辑、删除和版本语义。
7. **切片 D**：未来附件备份与 Zotero 迁移接口需要预留到什么粒度，但不要求首版实现。
8. **内置 AI Runtime**：首版 Runtime 的能力、会话、任务、确认和审计边界；具体供应商 API 格式
   留待该项目设计时确定。

## 20. 各切片转入实现计划的条件

为某一切片创建 `docs/superpowers/plans/...` 前，先满足共同条件：

- 只收敛 §19 中影响当前实施模块的问题；平台相关模块按各自测试矩阵记录已测与待测状态。
- 明确该切片的用户流程、数据迁移、跨平台差异和失败恢复语义。
- 将 §17 中属于该切片的场景改写为精确验收标准。
- 确认新模块不要求 core 感知 research 领域。

除此之外，各切片或子里程碑分别满足：

- **完整切片 A**：产品语义以 §4–§8、§11.1、§12–§14 和 §16–§17 为准，不再把 A2 的核心数据需求留到 A1
  实施后决定。
- **子里程碑 A1**：技术选型、macOS/Node.js 22 文件验证、目标规模基准和精确验收已记录在 §8.4、§17.2–§17.4，
  可以进入实施计划和开发。实施中准备覆盖正常、文件名混乱、精确重复、同 DOI 不同文件、多版本、不完整元数据、
  扫描型、损坏、超大、只读、缺失和中断的可重复导入样本。文件语义模块的 Windows 实测按 §19.2 单独记录，
  不阻塞其他 A1 模块；该模块在哪个平台发生变更，就在该平台先验证并保留另一平台待测状态。
- **子里程碑 A2**：设计边界在 A1 开工前已确认；逐文件实施计划在 A1 闭环验收后编写，不改变已确认的稳定身份、
  字段来源、文件位置、删除恢复和迁移出口语义。
- **切片 B**：准备覆盖常见与极端情况的真实测试 PDF，完成 PDF 与 OCR 引擎最小技术验证，
  并据此设定性能预算。
- **切片 C**：把批注 → 证据 → 观点 → 跨论文对照 → 来源回跳改写为完整用户流程和验收标准。
- **切片 D**：定义并实现 BibTeX、RIS、CSL JSON 基础适配契约及未来扩展边界；不以完整 Zotero
  迁移、附件备份或同步语义作为开工条件。

内置 AI Runtime 另行建立产品切片和实施计划；仅预留能力注册与兼容边界不会阻塞上述切片。
