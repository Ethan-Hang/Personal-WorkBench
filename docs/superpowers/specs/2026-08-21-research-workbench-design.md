# 独立论文管理与阅读工作台

日期：2026-08-21
状态：探索中，暂不排期
分支：`feat/research-workbench`
关联需求：`TASK-013`（仅作长期追踪编号；本文档不改变外部任务状态）

> 本文档用于保存已经形成的产品方向、用户痛点、设计原则和待验证假设。它不是实现计划，
> 不代表当前承诺开发，也不授权访问或更新任何外部任务系统。关联需求中的视觉原型只是一种
> 信息结构示例，不是必须复刻的界面、流程或验收标准。

## 1. 产品定位

Research Workbench 是 Personal WorkBench 内一个独立的论文管理、阅读与研究知识整理领域。
它不是 Zotero 的附属品，也不以 Zotero 数据库作为内部真相来源。

产品应当拥有自己的数据模型、文件管理、PDF 阅读、批注、检索和研究工作流。Zotero、
BibTeX、RIS、CSL JSON 等只位于互操作边界，用于迁移、导入、导出和必要的生态兼容。

目标工作流是：

```text
采集 / 导入
    → 去重与元数据确认
    → 文献库、目录与标签
    → PDF 阅读与上下文批注
    → 证据、观点与跨论文对照
    → 综述、写作和研究项目推进
```

产品差异化不来自“比 Zotero 多几个按钮”，而来自两点：

1. 更清晰、可恢复、不会重复占用空间的文件与知识组织方式。
2. 把“读过和高亮过”继续推进为可追溯的证据、观点和写作材料。

## 2. 当前已确认的痛点

### 2.1 文件保存与分类

- 同一 PDF 可能服务多个论文、课程或研究项目，不应因为出现在多个层级目录而重复保存。
- 同一 PDF 在不同研究目的下需要不同批注，不能被迫共享唯一一套标注。
- 文件夹树必须清晰直观，移动、添加到其他目录和删除引用的语义不能含糊。
- 文件去重不能破坏用户对论文版本、所属项目和阅读上下文的理解。

### 2.2 标签创建、治理与找回

- 标签入口过小或创建步骤繁琐会打断阅读。
- 标签长期积累后容易出现大小写、语言、单复数和近义词造成的重复。
- 标签如果只以大量小色块平铺，数量增加后无法浏览和维护。
- 用户有时记得概念或近义表达，却想不起当时使用的准确标签。

### 2.3 PDF 资源开销

- 打开过多 PDF 后，后台标签页不应持续占用完整渲染内存。
- 大型文档的解析、页面渲染、全文索引和 OCR 不应在打开瞬间同时争抢 CPU。
- 关闭或休眠文档后，页面 Canvas、文本层和中间缓存必须能够回收。

### 2.4 论文类型与引用元数据

- 论文、报告、预印本、标准、网页和其他材料不一定能落入严格的固定分类。
- 不完整或不规则来源不能因为缺少“正确类型”而无法保存。
- 作者、日期、载体、版本和标识符等引用信息需要灵活保存，并保留来源与原始字段。
- 引用输出格式不应反过来限制内部数据模型。

### 2.5 基础能力底线

- 基本 PDF 阅读器能力不能缺失。
- Zotero 已被验证有效的文献管理能力不能因为产品追求差异化而丢失。
- 兼容 Zotero 是次要目标，但用户的数据必须可迁移、可导出，不能形成新的锁定。

## 3. 已确认的产品原则

### 3.1 WorkBench 是数据真源

Research Workbench 自己管理论文、元数据、附件索引、阅读状态、批注和研究知识。
外部平台 ID 只用于建立映射，外部数据不得直接决定内部表结构。

### 3.2 论文、文件和上下文分离

“学术作品”“某一版本”“磁盘上的文件”“目录中的位置”和“为了某个目的阅读”是不同概念。
不能用一条记录或一个目录路径同时承担这些职责。

### 3.3 原始文件默认不可变

批注、笔记和阅读状态默认旁挂保存，不直接修改原 PDF。需要分享时可显式导出带批注副本。
这样才能可靠去重、校验文件完整性，并避免第三方工具写回导致原件变化。

### 3.4 本地优先、可恢复、可迁移

- 离线时仍能管理、阅读、搜索已有内容。
- 原始 PDF、元数据、批注和笔记都有明确导出路径。
- 导入、合并、移动和删除等高风险动作应可预览或撤销。
- 数据库损坏不能连带破坏原始附件。

### 3.5 性能是功能约束

大型 PDF、多文档标签页和长时间阅读是正常场景，不是事后优化项。实现前必须建立测试语料和
测量首次打开、翻页、搜索、峰值内存、后台休眠及关闭后回收等指标。

### 3.6 视觉原型不构成约束

与 `TASK-013` 关联的视觉材料仅用于说明“论文项目、阶段、研究资产、导师意见”等可能的
信息结构。最终导航、布局、步骤数量、进度表达和交互方式均需根据真实阅读工作流重新设计。

## 4. 领域概念草案

下表用于稳定讨论语言，不等同于最终数据库表。

| 概念                | 职责                                                                |
| ------------------- | ------------------------------------------------------------------- |
| `Work`              | 一项学术作品或研究材料的稳定身份，例如论文、报告、标准或网页        |
| `Edition`           | 作品的具体版本，例如 arXiv 预印本、会议版、期刊版和修订版           |
| `Asset`             | 按内容 hash 识别的物理文件；完全相同的 PDF 只保存一份               |
| `Attachment`        | `Edition` 与 `Asset` 的关系及文件角色，例如正文、补充材料或数据附件 |
| `Collection`        | 用户可见的层级目录或智能集合                                        |
| `CollectionEntry`   | `Work` 在某个目录中的逻辑引用，不复制物理文件                       |
| `ResearchProject`   | 毕业论文、课程报告、综述或其他长期研究目标                          |
| `ReadingContext`    | 一次具有明确目的的阅读上下文，通常关联研究项目或写作主题            |
| `AnnotationLayer`   | 某个阅读上下文下可独立显示、隐藏和导出的批注集合                    |
| `Annotation`        | 高亮、下划线、区域标注、评论、书签等定位到具体文件版本的标注        |
| `Evidence`          | 从原文和批注提炼、保留准确出处的证据卡片                            |
| `Claim`             | 可由多篇论文的证据支持、反驳或限定的研究观点                        |
| `Tag`               | 具有稳定 ID 和规范名称的跨目录描述                                  |
| `TagAlias`          | 标签的语言变体、缩写、旧名称和近义入口                              |
| `ExternalSourceMap` | Zotero、DOI、arXiv 等外部实体与内部对象的映射及同步游标             |

### 4.1 两级去重

必须区分：

1. **文件级精确去重**：相同字节得到相同 hash，只保留一个 `Asset`。
2. **作品级候选重复**：PDF 字节不同，但 DOI 相同或标题、作者、年份高度近似；只能提示合并，
   不得自动破坏版本关系。

线性化方式、下载站点或嵌入元数据不同都可能改变 PDF 字节，因此只用 hash 无法识别同一作品。

## 5. 文件与目录模型

### 5.1 一份文件，多处出现

- `Collection` 可以形成层级树。
- `Work` 与 `Collection` 是多对多关系。
- 把论文添加到另一个目录只创建 `CollectionEntry`。
- 从一个目录移除论文只删除该引用，不删除 `Work`、`Asset` 或其他目录引用。
- 真正删除文件前检查所有论文版本、附件和导出任务的引用，并先进入回收站。

### 5.2 文件夹视图

至少需要：

- 左侧目录树、展开状态、当前路径和数量。
- “全部论文、未分类、最近阅读、重复项、缺失文件、回收站”等系统视图。
- 面包屑和清晰的多目录归属提示。
- 拖拽时明确提示“移动引用”或“添加到另一个目录”。
- 批量归档、移动、添加标签和检查重复项。
- 文件夹与标签职责分离：文件夹表达主动组织，标签表达跨目录属性。

### 5.3 托管与链接模式（推荐默认，尚未确认）

推荐采用混合模式：

- **托管文件**：默认复制到内容寻址文件库，便于去重、备份和跨设备恢复。
- **链接文件**：保留用户现有磁盘位置，适合已有大量手工目录的用户。
- 界面目录是逻辑分类，不要求映射为真实磁盘目录。
- 支持显式“转为托管”和“导出到真实目录”。

待确认：第一版是否同时支持两种模式，还是先只做托管模式以降低实现和测试复杂度。

## 6. 阅读上下文与批注图层

### 6.1 目标行为

同一个 `Asset` 在多个目录或研究项目中仍只有一份文件，但可以拥有互不干扰的批注图层。
用户可以选择只看当前图层，也可以叠加查看其他图层。

### 6.2 推荐模型（尚未确认）

采用“通用批注层 + 多个命名上下文层”：

- 通用层记录与具体项目无关的核心理解。
- 研究项目层记录服务于毕业论文、课程报告或综述的批注。
- 文件夹或项目可以绑定默认图层，但移动目录不能改变批注所有权。
- 阅读器必须始终明显显示当前写入图层，避免批注被写进错误上下文后难以发现。

不推荐把批注严格绑定 `CollectionEntry`。目录重组后批注的研究含义不应随之漂移。

### 6.3 批注定位与版本

- 批注绑定具体 `Asset` 或 `Edition` 版本。
- 定位信息至少保留页码、页面坐标、文本引用和文本上下文指纹。
- PDF 版本变化后不得静默套用旧坐标；可以尝试迁移，但必须展示未匹配项。
- 批注、评论、证据卡片和导出副本之间需要可追溯关系。

## 7. 标签系统

### 7.1 标签不是小色块集合

标签应拥有独立的管理界面和治理能力：

- 规范名称、别名、说明、使用次数和最近使用时间。
- 按主题、方法、数据集、研究对象、阅读状态等维度分组。
- 创建时检测大小写、空格、语言、单复数和近似名称。
- 支持重命名、合并、批量替换、删除和查看受影响论文。
- 支持未使用、低频和疑似重复标签的整理建议。
- 颜色只作为辅助辨识，不作为标签的主要信息结构。

### 7.2 找回体验

- 模糊匹配规范名称和别名。
- 展示最近使用、常用和当前项目使用过的标签。
- 相似标签同时展示说明和代表论文，帮助辨别差异。
- 支持保存常用标签组合和多维筛选条件。
- AI 可以推荐已有标签，但默认不得未经确认批量创建新标签。

## 8. 元数据与引用

### 8.1 宽松内部模型

- 类型必须允许 `unknown`、`other` 和用户自定义值。
- 标题、作者、日期、期刊、会议、卷期页码等字段均允许缺失。
- 作者使用可扩展角色，而不是只有固定的作者和编辑。
- 日期可以分别表达发表、上线、接收、修订和访问时间。
- 支持 DOI、ISBN、ISSN、arXiv ID、PMID、URL 等多个标识符。
- 无法映射的外部字段必须保存在原始记录中，不能静默丢失。

### 8.2 字段级来源与冲突

每个关键字段应能够记录来源、获取时间和是否人工确认。多个来源冲突时逐字段比较，不能用
“整条记录覆盖”抹掉人工修正。

### 8.3 引用格式是输出层

内部模型不绑定某一种 BibTeX entry type 或 CSL item type。引用导出时再映射到目标格式，
并对无法准确表达的字段给出提示。不得为了兼容引用格式而阻止用户保存不完整材料。

## 9. PDF 阅读器能力底线

第一版可称为“阅读器”之前，至少应覆盖：

- 文档大纲、缩略图、页码跳转、缩放和常用页面布局。
- 全文搜索、文本选择和复制。
- 高亮、下划线、区域标注、评论和书签。
- 批注列表定位、图层切换及当前图层提示。
- 多标签页、最近阅读、阅读位置和缩放状态恢复。
- 键盘快捷键和基本无障碍操作。
- 原始文件打开、文件位置查看和带批注副本导出。

具体双页、连续滚动、夜间阅读、手写和触控能力在 UI 方案阶段评估，不能仅从视觉原型推导。

## 10. 阅读器性能约束

### 10.1 运行策略

- 只渲染视口附近页面，离开缓存窗口的 Canvas 和文本层可回收。
- 后台标签页进入休眠，只保留文档句柄和可序列化阅读状态。
- 页面渲染、解析和索引使用可取消的后台任务，切换文档后停止无用工作。
- 缩略图、正文页面、文本层和搜索索引分别按需加载。
- 使用有明确上限的 LRU 缓存，不随打开文档数量无限增长。
- 大型 PDF 使用安全模式，避免打开时一次性解析、渲染和索引全文。
- OCR 和全文索引只在空闲时执行，允许暂停，并避免阻塞当前页面阅读。

### 10.2 实施前必须建立的基准

在选定 PDF 引擎和运行形态前，准备小型、扫描型、图片密集型、超长和损坏边缘文档，测量：

- 首次可见页面时间。
- 连续翻页与快速跳页的 CPU 峰值。
- 单文档和多文档峰值内存。
- 后台标签页休眠后的保留内存。
- 关闭文档后的内存回收。
- 全文搜索和索引建立时间。

具体预算数值需基于目标设备与样本文档确定，本文档不提前编造阈值。

## 11. 从阅读到研究知识

### 11.1 导入箱与筛选

新论文先进入导入箱：

```text
导入
  → 检查文件与作品重复项
  → 获取并确认元数据
  → 删除 / 稍后读 / 精读
  → 选择目录、研究项目和已有标签
  → 正式入库
```

未整理内容不应直接污染正式目录与标签体系。

### 11.2 证据链

```text
原文定位
  → 批注
  → 证据卡片
  → 支持 / 反驳 / 限定观点
  → 跨论文对照矩阵
  → 综述或写作材料
```

证据必须保留作品、文件版本、页码、原文、批注图层和提取时间。写作材料应能返回准确出处，
不能退化为与来源脱离的普通文本片段。

### 11.3 论文项目工作流

可以在 Research Workbench 上层提供研究项目、阶段、里程碑、文献矩阵、方法模型、导师意见和
文稿版本管理。这些是候选能力，不绑定现有视觉原型的布局或固定八阶段流程。

只有“阅读这篇论文”“核实这条证据”“完成综述初稿”等可执行动作才投影为 core `Item`，
论文本身、批注和观点不属于通用待办。

## 12. 检索与重访

搜索范围至少包括：

- 标题、作者、年份、期刊、标识符和自定义字段。
- 文件夹、标签、研究项目和阅读状态。
- PDF 正文、批注、笔记、证据和观点。
- 缺失字段、重复项、缺失文件等维护条件。

结构化筛选、模糊搜索和保存查询应先于语义搜索可靠完成。语义检索可以补充“记得内容但忘了
标题”的场景，但不能成为基础检索不可用的补偿。

## 13. Zotero 优秀能力与互操作边界

### 13.1 不能丢失的基线能力

- 多级集合，以及一篇论文属于多个集合。
- 附件管理、缺失文件提示和重复项识别。
- DOI、ISBN、arXiv 等标识符辅助获取元数据。
- 安全的重复文献合并。
- 全文搜索、保存查询、标签、关联论文、笔记和批注。
- BibTeX、RIS、CSL JSON 等常见格式导入导出。
- 引用复制和基础参考文献生成。

“不能丢失”指产品能力和用户结果，不要求复制 Zotero 的界面、内部数据库结构或全部插件生态。

### 13.2 分阶段互操作

1. **基础互操作**：BibTeX、RIS、CSL JSON 导入导出，保留外部 key 和原始记录。
2. **Zotero 迁移**：导入条目、集合、标签、附件映射和能够可靠转换的批注。
3. **增量互操作**：根据真实需求评估外部 ID、游标和冲突处理。
4. **双向同步**：优先级最低；只有删除、版本、附件和批注冲突语义全部确定后才考虑。

不得把直接修改 Zotero 数据库作为基础方案。Connector、Word 插件和完整团队库不属于首轮目标，
但导出接口不能堵死未来接入。

## 14. 存储、备份与同步边界

- PDF 不作为 SQLite BLOB 保存；数据库只保存文件标识、路径、hash、大小、MIME、版本和状态。
- 当前账号数据库备份可以覆盖研究元数据、阅读状态和旁挂批注，但不会自动携带 PDF 附件。
- 附件备份、去重上传、恢复校验、配额和可选加密需要单独设计。
- 数据库恢复与附件恢复必须检测缺失和版本不一致，不能显示“恢复成功”却留下静默断链。
- 当前云端“保险箱”模型不等于多设备并发同步；研究模块不得暗中假设实时协作成立。

## 15. 仓库边界

Research Workbench 应作为独立领域进入 `modules/research`，遵守现有模块边界：

- 模块只能依赖 core，模块之间零依赖。
- core 不感知论文、PDF、Zotero、批注或研究项目。
- 模块拥有自己的迁移、存储适配器、契约、服务端注册和 UI 注册。
- 与应用壳层的前后端交接继续通过模块 `contract.ts` 和注册点完成。
- Todo、工作台与日历不直接依赖 research；research 只把可执行动作投影为 core `Item`。

可能的内部目录如下，仅表达职责，不是实施文件清单：

```text
modules/research
├─ library       作品、版本、集合和标签
├─ storage       文件索引、去重、回收站和附件状态
├─ ingest        导入箱、元数据识别和重复检测
├─ reader        PDF 阅读状态与性能策略
├─ annotation    批注图层、书签和笔记
├─ knowledge     证据、观点和综述矩阵
└─ interop       Zotero、BibTeX、RIS、CSL JSON
```

是否需要为 PDF 引擎、全文索引或外部元数据客户端增加独立 package，必须等技术验证后决定，
不能为了目录好看提前抽象。

## 16. 建议的产品切片

以下仅用于约束依赖顺序，不是 implementation plan：

### 切片 A：可信文献库

完成作品、版本、文件、目录、标签、导入箱、元数据来源和可迁移导出，先证明不会丢文件和字段。

### 切片 B：可长期使用的阅读器

完成基本阅读、阅读状态、批注图层和大型文档性能基准，证明连续使用不会失控占用资源。

### 切片 C：研究知识闭环

完成证据、观点、跨论文对照和来源回跳，让阅读结果能够进入综述与写作。

### 切片 D：生态兼容与附件保护

完善 Zotero 迁移、引用输出、附件备份与恢复。是否继续到双向同步由实际迁移痛点决定。

## 17. 关键验收场景草案

在编写实施计划前，至少把以下场景变成可验证标准：

1. 同一 PDF 导入两次，磁盘只保留一份，论文可出现在多个目录。
2. 同一 PDF 在两个研究上下文中拥有不同批注，并可选择叠加显示。
3. 删除一个目录引用不会删除其他目录中的论文、批注或物理文件。
4. 两份字节不同但 DOI 相同的 PDF 被提示为作品级候选重复，不自动丢弃任一版本。
5. `unknown` 类型和不完整元数据可以保存、搜索、编辑并无损导出原始字段。
6. 近似标签能够合并并保留别名，既有论文不丢失关联。
7. 多个后台 PDF 休眠后释放页面渲染资源，关闭文档后缓存可回收。
8. 大型 PDF 打开时不自动同时执行全文渲染、索引和 OCR。
9. 从证据卡片可以回到准确论文、版本、页码和原文位置。
10. 即使不使用 Zotero，全部核心功能仍然成立；即使离开 WorkBench，数据仍可导出。

## 18. 明确暂缓或不做

- 不把视觉原型当作固定页面设计或阶段模型。
- 不以复刻 Zotero UI、数据库结构或全部插件为目标。
- 不在首轮实现 Zotero 双向同步、Word 插件或团队协作库。
- 不从第一天自研完整 CSL 引擎，优先采用成熟实现并保持输出适配层。
- 不默认把批注直接写回原 PDF。
- 不让 AI 未经确认自动创建大量标签、修改元数据或合并论文。
- 不把实时多端协作、CRDT 或服务端常驻部署夹带进本模块。
- 不在设计未确认时创建详细 implementation plan 或数据库迁移。

## 19. 尚未决定的问题

以下问题会实质改变实现，进入 implementation plan 前必须逐项确认：

1. 第一版采用纯托管文件库，还是托管为主、外部链接为辅的混合模式。
2. 批注是否采用“通用层 + 命名上下文层”，以及目录如何选择默认图层。
3. 目标运行形态是否保持浏览器 + 本地 server，或为文件系统和 PDF 性能增加桌面外壳。
4. 第一版支持哪些 PDF 功能、输入设备和快捷键。
5. 用哪些真实文档构成性能基准，目标设备与内存预算是什么。
6. 元数据提供方和优先级，以及字段冲突时的默认行为。
7. Zotero 第一阶段迁移到何种粒度：条目、集合、标签、附件、笔记、批注。
8. 附件是否进入现有 WebDAV，以及加密、配额、断点续传和恢复校验方式。
9. 论文项目、里程碑、导师意见和版本管理在首版中的优先级。
