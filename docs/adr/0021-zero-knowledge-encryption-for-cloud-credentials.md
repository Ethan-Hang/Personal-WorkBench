# 0021. 云端凭据的零知识加密

日期：2026-08-19
状态：已接受

## 背景

「记住一个 GitHub 账号，其余自动接上」需要把 WebDAV 凭据与应用设置存到一处云端、
跨设备可读写的地方。方案选的是 GitHub secret gist：轻量、免额外基础设施、复用已经
实现的 GitHub Device Flow 登录。

**核心事实：secret gist 不是私有的。** 它只是不出现在搜索与索引里，任何拿到 URL 的人
**无需登录**即可读到全文。GitHub 账号本身的安全性（是否开二次验证、是否复用密码）
因此直接决定了明文存在 gist 里的任何东西是否会泄露。而 gist 里恰好要放 WebDAV 的
用户名与密码——这是能直接搬空整个异地备份保险箱的凭据，不是无所谓的数据。

## 决策

**Gist 里存的 WebDAV 凭据与设置，一律用口令派生的对称密钥加密，密文才上传。**
GitHub 被盗不等于 WebDAV 被盗——这是「零知识」在本设计里的具体含义：GitHub 只拿到
密文，解密口令从不经过它。

### 加密原语：`node:crypto` 就够，不引入任何依赖

```
scryptSync(口令, salt, 32)  →  AES-256-GCM(iv 12B)  →  header 明文 + data 密文
```

**不引入任何第三方加密库，更不引入原生模块。** 这对 `npm run setup` 用
`--ignore-scripts` 跳过原生编译这件事很重要——一旦引入需要编译的依赖，`setup` 的
免编译前提就被破坏。`node:crypto` 内置的 `scrypt` 与 `AES-256-GCM` 是 Node 自带能力，
零新增依赖。

### 三个具体设计点

1. **口令验证不单独存 verifier。** GCM 自带认证标签，解不开就是口令错，不需要额外
   存一份「口令对不对」的校验值。少一个字段，也就少一个能被离线暴力破解的靶子——
   独立 verifier 本质上给攻击者提供了一个可以脱离网络、无限次尝试的判定 oracle。
2. **salt 只在改口令时更换，不是每次写都换。** `scrypt` 刻意设计得很慢（这正是它抗
   暴力破解的方式），每次改一条设置就重新派生密钥会带来明显可感知的卡顿。salt 复用
   不削弱安全性——它保护的是「同一密钥不因为 salt 复用而被跨会话关联攻击」，只要
   salt 本身不被口令强度以外的手段攻破即可。
3. **header 保持明文**（`v` / `kdf` / `salt` / `iv` / `updatedAt` / `device`）。列表
   展示与「云端是否比本地更新」的冲突判断不需要解密就能完成，而这些字段本身不泄露
   任何业务内容。

**Gist 里绝不存 GitHub token 本身。** 只有 WebDAV 凭据与应用设置。token 失效的后果
被严格限定在「需要重新登录」，不会连带暴露其他凭据。

### 两档威胁模型，只有一档需要强制加密

| 位置                                                | 威胁模型                              | 处理                                |
| --------------------------------------------------- | ------------------------------------- | ----------------------------------- |
| GitHub Gist                                         | 任何拿到 URL 的人都能读，且不需要登录 | **强制加密**，唯一真正的攻击面      |
| 本地凭据（OS 保管库 / `credentials.json` 退化路径） | 泄露的前提是攻击者已经能读本机文件    | OS 凭据管理器是**增强项**而非阻塞项 |

本地文件泄露意味着攻击者已经在这台机器上有文件读取能力，那么本地的 SQLite 数据库
本身也已经全部泄露——给本地凭据文件加密并不能在这个威胁模型下带来实质收益，却会
让「OS 保管库不可用」这个边界情况的实现复杂度和阻塞面都上升。因此本地存储优先用
OS 凭据管理器，不可用时退化到 `data/local/credentials.json` 明文存储，并在设置页
明确提示「本机凭据未受系统保管库保护」，实现不因此被卡住。

### 忘记口令的后果有界

忘记加密口令的后果被限定为「需要重新填一次 WebDAV 凭据」，**数据不会丢**——真正的
数据在 WebDAV 上，Gist 里只有一份可以重建的凭据。这条边界是刻意设计出来的：口令
遗忘不该成为数据丢失的诱因。

## 后果

- GitHub 账号泄露（或 gist URL 意外流出）不直接等于 WebDAV 账号泄露，攻击者还需要
  拿到加密口令
- 零新增依赖，`npm run setup` 的免编译前提不受影响
- 忘记口令的代价有界且可恢复，不会连带丢数据
- **必须诚实记录的限制：WebDAV 上的备份文件本身未加密**（见 ADR-0020）。零知识加密
  覆盖的只是「凭据与设置」这条链路，不覆盖已经上传到网盘的 `.db.gz` 快照——那份数据
  的机密性完全依赖网盘账号自身的安全性。若将来要做端到端加密备份，可以复用本 ADR
  的加密原语，但需要重新评估：恢复流程里的差异计算（ATTACH 两个库直接比对）需要先
  解密整份快照，届时 preflight 的成本会显著上升，不是简单的复用
- **代价**：多了一个必须记住的口令；口令强度完全决定了 Gist 侧凭据的实际安全性，
  弱口令下 `scrypt` 的抗暴力破解能力也有上限
- **关闭的选项**：
  - **明文存 Gist**——否决理由即背景所述的核心事实：secret gist 对任何拿到 URL 的人
    都是可读的，明文等于把 WebDAV 密码公开托管
  - **改用私有 repo 存凭据**——需要把 OAuth scope 从 `gist` 扩大到 `repo`，
    `repo` 权限能读写用户的全部仓库，对「只是想存一份凭据」这个需求而言权限过宽，
    且不会消除「凭据本身是否加密」这个真正的问题，只是换了个同样需要信任的容器
