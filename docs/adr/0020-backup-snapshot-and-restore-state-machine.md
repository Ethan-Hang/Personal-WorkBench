# 0020. 备份快照与恢复状态机

日期：2026-08-19
状态：已接受

## 背景

本地优先应用的数据只存在于一台机器上，换机、硬盘坏、误删都会造成不可逆的数据丢失。
上云的第一诉求是「数据不会丢」，落地为「能异地备份、能从备份恢复」。

### 一条实测发现，决定了整个方案不能是什么

```
workbench.db 磁盘大小 ...... 4,096 字节（1 页）
逻辑数据库大小 ............. 180 KB（45 页）
workbench.db-wal ........... 2.2 MB
```

`journal_mode = WAL` 从建库起就没 checkpoint 过：**此刻全部真实数据都在 `-wal`
文件里，主库文件几乎是空的。** 因此任何「用 `fs.copyFile` 把 `workbench.db` 拷到云上」
的方案都是错的——拷出来的库能正常打开、结构完整、**没有数据，而且不会报任何错**。
这个坑不会在开发时暴露，只会在真正需要恢复的那一刻暴露。

第二个前置发现：模块仓储的数据库连接在构造时被按值捕获，进程运行期间换不掉
（`private readonly db`）。「恢复」与「账号切换」（见 ADR-0019）本质是同一件事——
在进程不重启的前提下换掉底层连接——因此两者共享同一个连接持有层前置能力。

## 决策

### 快照：一律走 SQLite 官方 Online Backup API

**禁止使用 `fs.copyFile` 复制数据库文件。** 快照统一走 `better-sqlite3` 自带的
`db.backup(filename)`（SQLite 官方 Online Backup API），它产出单个一致性快照文件，
自动含 WAL 内容，不需要手动 checkpoint，也不需要处理 `-shm`。

### 备份：靠上传顺序换原子性

```
db.backup(tmp) → gzip → PUT <timestamp>.db.gz → PUT <timestamp>.meta.json
```

**先传数据、再传元数据。** WebDAV 协议本身给不了原子性，那就用上传顺序编码它：
中间断网只会留下一个没有 `.meta.json` 的孤儿 `.db.gz`，列表页可以据此判断「不完整」
并清理，不会有半份数据被当成一份完整备份误用。

**元数据旁挂，不内嵌进快照。** 判断「这份备份能不能恢复到当前代码」不该为此下载
整个库。`.meta.json` 记录 `createdAt`、`accountId`、`counts`（表行数）、`sha256`，以及
**`migrations`——每条迁移谱系各记一个水位**：

```json
"migrations": {
  "__drizzle_migrations": 1755400000000,
  "__drizzle_migrations_modules_todo_migrations": 1755300000000,
  "__drizzle_migrations_modules_campus_recruit_migrations": 1755200000000
}
```

单一个版本号在这里是错的——这正对着项目已有的「模块迁移各记各账」设计：`core`、
todo、campus-recruit 三条迁移谱系各自使用独立的记账表（见迁移各记各账相关设计），
可以各自领先，一个全局版本号无法表达这种状态。

### 恢复：五态机

```
idle
 └→ preflight            下载 → 解压 → integrity_check → 水位比对 → 算差异
     └→ awaiting-confirm      展示差异，等确认（可取消，无副作用）
         └→ restoring         ← 从这里开始全服务 503
             ├ 1 snapshot-local   db.backup(rollback.db)   ← 回退点
             ├ 2 swap             关连接 → 删 db/-wal/-shm → rename → 开连接
             ├ 3 verify           integrity + foreign_key_check + 跑迁移 + 探针查询
             └ 4 done → idle
                 ↓ 任一步失败
             rolling-back        同样的 swap，源换成 rollback.db
                 ├ 成功 → idle（「已回到恢复前」）
                 └ 失败 → failed（不自动重试，日志给人工指令）
```

四个承重细节：

1. **没有回退点就不动手。** 第 1 步 `db.backup(rollback.db)` 失败，整个恢复直接拒绝
   开始，不进入任何有风险的步骤。
2. **第 2 步必须显式删 `-wal` 与 `-shm`。** 只替换主库文件、留下旧 WAL，旧数据会在
   下次打开时复活并覆盖刚恢复的内容——**且不报任何错**。这是「背景」里那个 WAL 坑的
   反面：上次是「拷贝时数据全在 WAL 里所以拷丢了」，这次是「换库时残留的旧 WAL 把
   刚恢复的数据又盖回去了」，两者是同一个事实的两种事故。
3. **备份比代码新则拒绝恢复。** 水位比对三种结果：相等→直接恢复；备份更旧→恢复后
   跑迁移（正常升级路径）；**备份更新→拒绝**，返回 409 并说明具体是哪条谱系差多少
   版本。向下迁移不存在，硬恢复的症状是运行时 `no such column`，比对在 preflight
   阶段用 `.meta.json` 完成，不需要下载库本身。
4. **恢复中断电不能变砖。** `.restore/state.json` 记录当前步骤，进程重启时若发现它
   存在，直接进入恢复态并提示「上次恢复停在 swap，可回退或重试」，而不是当作
   一切正常继续启动。

### 恢复模式：全服务暂停，而非只挡写

`restore-gate` 作为全局 `preHandler`：状态非 `idle` 且请求路径不在白名单
（`/api/health`、`/api/restore/*`）一律 503。理由不是「保守」，而是精确：换文件的
那一刻，读请求和写请求一样会读到碎的中间状态——只挡写挡不住这个问题。前端全局
`onError` 认这个 503 就切换到全屏恢复界面，多个标签页因此自动同步，不需要额外的
广播机制。

### 自动备份与自动清理：默认关闭，且共用一个开关

`backup.autoEnabled`（默认 `false`）与 `backup.retentionCount`（默认 `10`）落在既有
`app_settings` KV 表，是 `packages/core/src/settings.ts` 的 `SETTINGS_CODECS` 新增的
两个设置项（连同一个新增的 `count(fallback, min, max)` codec）。这是该文件本就自带的
扩展点——加一个设置项只需加一行，不需要新建表或写迁移——不算破例：`core` 拥有的是
应用级设置，备份配置不是模块的私有状态。

自动清理跟随同一个开关，而不是独立配置：关着自动备份、却在背后悄悄清理手动上传的
备份，是自相矛盾的行为——用户没有主动要求自动化，自动删除又是不可逆操作。默认关闭
的直接好处是：默认配置下零出站网络请求，本地优先的定位不因为「装了这个功能」而被
稀释。

**不引入常驻调度器。** 自动备份挂在进程启动时机检查，与项目里「重复任务的物化挂在
`listToday` 里顺手触发」是同一种取舍：本地优先的应用没有常驻调度器。

## 后果

- 备份 / 恢复链路对「数据其实在 WAL 里」这件事免疫，`db.backup()` 保证快照永远是
  完整一致的
- 恢复失败有明确、已验证过路径的回退点，不会出现「恢复了一半、库处于未知状态」
- 恢复期间全服务不可用（除健康检查与恢复接口本身），换来的是排除了「读到碎数据」
  这整类问题，代价是这段时间应用完全不可操作
- 元数据与迁移水位的设计使恢复前置校验（preflight）不需要下载整个库就能判断兼容性
- **代价**：备份未加密（明文 `.db.gz`），依赖 WebDAV 网盘账号自身的安全性——这一点
  在 ADR-0021 中另有说明；自动备份默认关闭意味着不主动开启的用户不会获得异地保险，
  这是刻意的选择而非疏漏
- **关闭的选项**：
  - `fs.copyFile` 做快照——会在 WAL 未 checkpoint 时静默丢失全部数据，且不报错，
    是此设计要规避的头号事故源
  - 元数据内嵌进快照文件——会导致「判断一份备份能不能恢复」需要先下载整个库
  - 恢复模式只挡写、不挡读——挡不住「换文件那一刻读到碎状态」这个真正的问题
