# 0019. 账号体系与每账号独立数据库

日期：2026-08-19
状态：已接受

## 背景

数据上云需要「换设备能接上」与「一台设备上能装多份数据」，这意味着系统第一次需要
身份概念：本地账号与 GitHub 账号并存、可切换。

ADR-0001 明确关闭过这条路：「不做账号体系」，并预言「若将来要做多用户，账号与数据
隔离需要一次真正的重构，而非增量」。这条预言在它设想的路径上是对的——共享一个库、
所有表加 `user_id`，确实要动 core 的 schema，牵连每一张表、每一条查询。

但还有第三条路，是 ADR-0001 当时没有列举的：**隔离做在文件边界，而不是行边界。**

## 决策

**每账号一个独立的 SQLite 文件**，账号切换 = 换连接指向的文件，不是换 WHERE 条件。

- `data/local/accounts/<accountId>/workbench.db`，每个账号自己一份完整的库（含 core
  与全部模块的表）
- 账号注册表 `data/local/accounts.json`，记录 `activeId` 与账号列表（`id` / `kind` /
  `displayName` / `avatar` / `dbDir` / 时间戳，GitHub 账号另加 `github: { login, userId, avatarUrl, gistId }` 字段）
- **该注册表用 JSON 原子写（写临时文件 + rename），不用 SQLite。** 理由是鸡生蛋：
  要先能读到账号列表，才知道该打开哪个库文件——用 SQLite 存它，等于要一个数据库来
  告诉你去哪找数据库。JSON 还有个人机友好的好处：文件万一损坏，可以直接用记事本修，
  SQLite 库损坏则通常直接打不开
- **头像设置与个人资料修改是纯元数据操作（`PATCH /api/accounts/:id`）**：头像支持用户自定义
  （本地上传图片裁剪压缩保存为 base64、精选矢量预设、图片 URL）、GitHub 官方头像自动联动以及系统默认头像。
  解析优先级为：`自定义 avatar > GitHub 头像 > 默认经典图标`，零触碰底层数据库文件
- **绑定 / 解绑 GitHub 账号不改账号 `id`、不改 `dbDir`。** 二者是纯元数据操作：往
  `accounts.json` 里加/删一个 `github` 字段，零文件系统动作。绑定时将 Device Flow 授权凭据
  由组合根存入本地系统保管库（`SecretStore`）；解绑与删除账号时由组合根联动清理对应凭据。
  若绑定时顺带把 `local-default` 改名成 `gh-Ethan-Hang` 之类，就需要连带重命名数据目录，一次失败
  就可能留下一个账号条目找不到对应库文件的悬空状态
- 同一个 GitHub 账号不能绑定两个本地账号（按 `github.userId` 在 `accounts.json`
  层面校验唯一），否则两个库会向同一个 Gist 写设置、互相覆盖

**推翻 ADR-0001 的哪一半，说清楚：**

| ADR-0001 的判断                              | 现状                                                                            |
| -------------------------------------------- | ------------------------------------------------------------------------------- |
| 不做多用户、不做权限模型、不做服务端账号体系 | **仍然成立**——本设计是单机上的多份本地数据 + 一个 GitHub 身份，不是服务端多租户 |
| 单一数据库文件                               | **被推翻**——现在是每账号一个文件                                                |
| 系统内无身份概念                             | **被推翻**——`accounts.json` 引入了账号 id                                       |

**为什么没有付出 ADR-0001 预言的代价：** 那句预言描述的是它设想的唯一路径——共享一个
库、所有表加 `user_id` 列、每条查询加过滤条件，这条路径下账号隔离确实要动 core 的
schema 与几乎每一处查询，是名副其实的「一次真正的重构」。每账号一个库文件是第三条路：
隔离发生在文件系统层，`packages/core` 的 schema 一行未改，三条铁律（模块只依赖
core、core 永不感知模块、模块自带迁移）无一被破坏。唯一动了 core 的地方是
`SETTINGS_CODECS` 新增两个备份相关设置项（见 ADR-0020），那是设置子系统自带的扩展点，
与账号隔离本身无关。

实现这条路径需要一个前置能力：连接持有层——模块仓储从「构造时拿到一个连接」改成
「拿到一个取连接的函数」`() => Database.Database`，使得账号切换（以及备份恢复）能在
进程不重启的前提下换掉底层连接。这不新增任何跨包接口，`core` 不参与注入。

## 后果

- **换设备、装多份数据、绑定云身份**三件事都成立，且不需要服务端账号体系或权限模型
- **账号切换必须跑一次模块迁移**：另一个账号的库可能是更旧版本代码建的，`core` 与各
  模块的迁移谱系需要各自追平
- **前端切换账号后必须全量失效查询缓存**，否则会看到上一个账号的残留数据，且因为
  乐观更新的存在，这类残留会以很难复现的方式间歇出现
- **代价**：每个账号是完整独立的一份库，账号之间不能共享任何数据（例如两个本地账号
  之间没有「共用一份秋招投递记录」这种能力）——这是有意的：账号本来就代表「互不相干
  的一份数据」，不是「同一份数据的不同视角」
- **关闭的选项**：共享一个库 + 全表加 `user_id` 列。否决理由是它会真正牵连 core 的
  schema 与每一条查询，且与「模块自带迁移、core 永不感知模块」的既有约束正面冲突；
  每账号一个文件把隔离完全下沉到文件系统边界，对 core 是零感知的
