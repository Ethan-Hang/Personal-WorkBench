# 0023. 习惯不是 core Item，且本地日期由前端提供

日期：2026-08-21
状态：已接受

## 背景

主设计文档 §8.5 在没有产品细节时留下过一条推测：

> 重复规则归模块所有：习惯模块自存 RRULE，按需展开为一条条具体的 core Item。

这条推测有它的道理——它当时要回答的问题是「要不要给 core Item 加 `recurrence` 字段」，
答案是不要。但它顺手多回答了一个当时没人问的问题：习惯**展开成什么**。

真正开始设计习惯模块时，这个附带结论站不住了。同时暴露出第二个问题：习惯打卡天然是
「本地哪一天」的概念，而模块**拿不到时区**。

## 决策

### 1. 习惯不生成 core Item

习惯只存在于自己的两张表里，不投影成 `items` 行，因此不出现在周日历、不进今日事项
聚合、不参与排程、不进回收站、不参与优先级派生。

理由不是「省事」，而是**语义**：core Item 的定义是「一件有具体时间的具体事」。
「每天阅读 30 分钟」不是一件事，是一条规则；把它每天展开成一条 Item，日历上就会出现
五六条每天重复、永远不需要排程的条目，把真正需要安排时间的事挤掉。

与 todo 重复任务的对比是这条决策的关键论据。todo **必须**物化成真实 Item，因为一条
重复出来的待办要能被排程、被拖到日历上、被完成、被丢进回收站——它与手工建的待办
在系统里完全同形，这正是那套设计的价值所在（见 CLAUDE.md「重复任务：物化，不是规则求值」）。
习惯不需要这些能力中的任何一个。为不需要的能力付物化的代价，是纯粹的负担。

由此得到一条更一般的判据，供下一个模块参考：

> **要不要投影成 core Item，取决于它是否需要 core 提供的跨模块能力**
> （排程、日历、今日聚合、优先级）。需要就投影，不需要就不投影。
> 「它看起来像一件事」不是理由。

### 2. 不物化每日实例，一切派生

`habit_checkins` 只存**真的发生过的打卡**。没打卡的日子不占行。「今天该做哪些」
「连续多少天」「完成率」全部由纯函数从规则与打卡记录算出。

被否决的方案是每天为每个习惯预生成一行 `pending`。它的好处（查询简单、能表达
「明确跳过」第三态）没有对应的真实需求，代价却是要照搬一整套物化 + 水位 + 幂等机制，
并且每年产生数千行没有信息量的记录。

一条随之而来的性质：**改频率不需要回填或清理历史**。规则变了，派生结果自然跟着变，
没有「旧实例怎么办」这个问题存在。

### 3. 本地日期由前端提供，不扩 `ModuleContext`

`ModuleContext` 只暴露 `moduleId` 与 `items`，模块拿不到 `SettingsRepository`，
而时区存在 `app_settings` 里。因此服务端算不出「今天是几号」。

决策是**不为此改 core**，改用既有约定：日期由前端算好再发。写操作的 body 同时携带
`date`（操作哪一天）与 `clientToday`（客户端本地今日），服务端用后者校验 7 天补卡窗口。

这与排程「`start` / `end` 是 UTC 时刻，由前端换算好再发」是同一条道理的两次应用：
**前端知道用户在哪个时区，服务端只知道自己进程的时区。**

被否决的两个替代方案：

- 服务端用 `new Date()` 装作知道时区。跨时区旅行时窗口校验会错，**而且不报错**。
- 给 `ModuleContext` 加 `settings`。为一个模块的一处校验扩 core 的能力槽，
  且一旦加上，此后每个模块都会顺手依赖它，`ModuleContext` 最小化的价值就此流失。

## 后果

**好的：**

- 习惯模块是**第一个「有自有表、但零 core Item」的模块**。秋招证明了模块可有自有实体
  （`migrations` 非空、投影进 core），工作台证明了模块可零自有表（`migrations: []`、
  只消费 core），习惯补上第三格：有自有表、不碰 core。三条铁律仍未破，core 一行未改。
- 存储上只保留一件事：**你真的做了**。数据的含义没有歧义。
- 日历不会被每日重复条目淹没。

**代价：**

- 习惯**无法被拖到日历上排时间**。「晚上八点复盘」这种有固定时段的习惯，只能靠自己
  另建一条 todo。若将来这个需求真的出现，正确的做法是给单个习惯加「同时生成 Item」
  开关，而不是推翻本条决策。
- `clientToday` 是个可以被伪造的入参。单人本地应用里这不构成威胁模型，但它在契约里
  确实是一处诚实标注的不对称，而不是疏漏。
- streak 与完成率每次都要扫一段打卡历史。单人数据量下不是问题；若真的慢了，加索引或
  缓存，**不要**因此回头去物化。

## 推翻的内容

本 ADR 推翻主设计文档 §8.5 中「习惯按需展开为一条条具体的 core Item」这半句。
§8.5 的主结论——**不给 core Item 加 `recurrence` 字段，复杂性向模块推**——完全保留，
本决策正是它的又一次应用。
