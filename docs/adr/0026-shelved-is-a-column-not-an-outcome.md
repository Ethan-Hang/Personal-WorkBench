# 0026. 泡池子是一列，不是 outcome 的一个取值

日期：2026-08-23
状态：已接受

## 背景

秋招统计页一直有「泡池子」一格，管理界面却标不了——它只能由 `deriveApplicationStatus`
按「无任何轮次 + 投递超 90 天」自动判出来（原设计见
`docs/superpowers/specs/2026-08-17-campus-recruit-module-design.md` §5）。

实际使用里这条派生规则两头都不对：

- **想标的时候标不了。** 收到「进入人才库」通知是一个有确切时刻的事件，用户当场就想记，
  而不是等 90 天让系统猜。变通做法是加一轮 `kind='other'` 的轮次写上「泡池子」，
  但那**恰好把这条投递永久排除出泡池子判定**（判定要求轮次数为 0），状态反而变成
  「流程中 · 其他」，统计里 `shelved` 恒为 0。用户观察到的正是这个。
- **同一轮改动让自动规则彻底失效。** 「标记已投递自动补一轮简历初筛」落地后，所有投递的
  轮次数都不再是 0。

原设计给出的理由是 ADR-0003 对 urgency 的那条——手动状态无人回头更新。那条理由在这里
不成立：urgency 是随时间连续变化的量，泡池子是一个离散事件。

## 决策

**新增可空列 `shelved_at`（instant），手标为主、派生兜底。**

- 契约的写入面是 `shelved: boolean`，服务端负责落时刻；**已经泡着的再标一次不刷新时刻**
  ——「从哪天开始没消息」才是有用的那个信息。
- 判定顺序：offer / oc / declined → 已挂 → **手标泡池子** → 待投递 → 自动泡池子 →
  已投递 / 流程中。已挂排在手标之前：泡着泡着挂了，显示「已挂」更准。
- 自动判定的条件从「无任何轮次」改成「**全部轮次仍 `pending`**」。

### 为什么不加进 `APPLICATION_OUTCOMES`

那是最省事的写法（UI 只要多一个 `<option>`），但有两个代价：

1. **SQLite 改 CHECK 约束必须整表重建。** `campus_recruit_applications` 上有
   `ck_campus_recruit_applications_outcome`，而 `campus_recruit_rounds` 有外键指向这张表。
   重建父表时引用会被改指向临时表名，是 SQLite 上的经典踩雷点。为一个状态值冒这个险
   不值得——新增一列的迁移是一行 `ADD COLUMN`。
2. **语义会被拧变形。** 泡池子不是终局：今天泡着，下周可能突然来面试。把它放进 outcome
   意味着撤销它要被表达成「清空终局结果」，而这两件事在用户脑子里不是一回事。

## 后果

- 前端的「终局状态」下拉合并了两个互斥概念，**选中一个必须显式清掉另一个**，否则会留下
  「既 Offer 又泡池子」的记录。这段映射抽在 `modules/campus-recruit/src/ui/utils/outcomeSelect.ts`
  ——`.ts` 进 Vitest 收集范围，因此有单测护着；放在 `.tsx` 组件里就没有。
- `ApplicationStatusCode` 的 `shelved` 现在有两个来源（手标与派生），但它们指向同一个状态
  码与同一个标签，因此不会出现 ADR-0009 警惕的那种「两个真相」。
- 与 ADR-0009 恰好相反的结论：那次是**借用** core 已有的枚举值表达模块自己的概念，这次是
  **拒绝**往模块自己的枚举里塞一个不同类的值。判据是同一条——看这个值和枚举里其余取值
  是不是同一类东西。`cancelled` 与「在回收站中」都是「这条不再活跃」；`shelved` 与
  `offer / rejected` 不是同一类，前者可撤销、后者是终局。
