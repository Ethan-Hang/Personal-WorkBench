# ADR-0014：todo 长出自有表——子任务、标签与重复任务

日期：2026-08-18
状态：已接受

## 背景

todo 此前是**零自有表模块**（`migrations: []`），纯粹活在 core 的 `Item` 上。
本次一次性加入四项能力：备注、子任务、标签、重复任务。

备注不需要新表（core 的 `Item.notes` 一直闲置），另外三项需要。这是 todo 第一次
携带自己的迁移，因此也是第三条铁律「模块自带迁移与注册项」在 todo 上的第一次落地。

## 决策

### 1. 子任务是纯文本勾选项，不是 core Item

`todo_subtasks` 只有「标题 + 勾没勾 + 排序位」。子任务**不能单独排程、不上日历、
不进回收站**。

否决的方案是让子任务也成为 core `Item`。那需要 core 的 `Item` 长出 `parentId`，
而 CLAUDE.md 写着「加模块时发现必须改 `packages/core/`，停下来想清楚」。这里想清楚的
结论是：`parentId` 会让每个消费 `Item` 的地方（日历、工作台今日页、待排程抽屉）
都要回答「子项要不要单独显示」，而收益只是「子任务也能排程」——一个尚未出现的需求。

代价：将来若真需要「把子任务提升为独立待办」，要写一次搬运逻辑。可以接受。

### 2. 标签是 todo 内部概念，不跨模块

`todo_tags` + `todo_task_tags`。**已知代价：工作台今日页看不见也筛不了这些标签。**

跨模块标签需要标签成为 core 级概念，秋招的 Item 也要能打标签。那是另一个量级的
改动，且会立刻撞上一个设计问题：秋招的 Item 是 `reconcileAllProjections` 生成的投影，
手工打的标签会被下次对账覆盖——与 ADR-0012 记的「手动给秋招 Item 排程会回弹」同源。

想让标签跨模块时，先解决那个问题，再回来改这条。

### 3. 重复任务用物化，不用「1 条 Item + 规则」

`todo_recurrences` 存规则，`todo_recurrence_items` 记「哪条规则在哪一天生成了哪条 Item」。
规则本身**不是待办**，它按需生成真正的 core `Item`。

选物化的理由：**日历、排程、完成、回收站全部零改动，core 一行不改。** 一条重复出来的
待办与手工建的待办在系统里完全同形，因此不需要在每个消费端各写一遍「这条是重复的吗」。
冒烟时可以直接看到效果：建一条「每周一三五」的规则，实例立刻出现在
`GET /api/workbench/calendar` 里，而工作台完全不知道「重复任务」这个概念存在。

否决「1 条 Item + 规则」的理由：日历取数、`localDayRange` 区间查询、以及「完成这一次
vs 完成整个系列」的语义全都要重做，且很可能逼着改 core。

物化的三条配套决定：

- **视野 90 天**（`MATERIALIZE_HORIZON_DAYS`）。日历区间端点上限本就是 96 天，
  90 天足够任何视图；无限展开会让一条「每天」的规则灌进几千条 Item。
- **幂等，靠复合主键而非水位**。`(recurrence_id, occurrence_date)` 是主键，
  因此 `materializeAll` 可以在每次 `listToday` 时无脑调用。`materialized_through`
  只是省掉重复展开的优化，**不是正确性的依赖**——水位丢了重跑也不会产生重复实例。
  本地优先的应用没有常驻调度器，「每次查询顺手补齐」是唯一可靠的触发点。
- **不补生成过去**。物化起点不早于今天，否则新建一条 `startDate` 在半年前的规则
  会凭空造出一百多条逾期待办。

改规则时只允许改「往后」的部分（标题 / 重要度 / 备注 / 截止日）。`freq`、`interval`、
`by*`、`startDate` 不可改——改了就得回收并重算全部未来实例，那与「删掉重建」没有区别，
却多一整套容易出错的对账逻辑。

删规则时**清掉未完成的实例，保留已完成的历史**。一律全删会让「上周确实做过的三次」
凭空消失；一律全留则会在日历上留下一串无主的未来待办。分界线放在「完成与否」而不是
「过去 / 未来」——昨天没做的那条该跟着规则一起消失。

### 4. 每月 31 号在没有 31 号的月份跳过

不顺延到 3/1，也不回退到 2/28。顺延会让一条规则在某些月份生成两次；回退会让
「月底」这个语义悄悄变成「月中」。跳过是唯一不改变规则含义的选择。

### 5. 每个模块的迁移记账表独立

**这是本次发现的一个既有隐患，不是新引入的。**

drizzle 的迁移器用**一张表里的一个全局水位**判断某条迁移该不该跑
（`sqlite-core/dialect.js`：`Number(lastDbMigration.created_at) < migration.folderMillis`）。
所有模块共用 `__drizzle_migrations` 时，先跑的模块只要时间戳更新，后跑模块的迁移
就会被**静默跳过**——没有任何报错，只有后续查询时的 `no such table`。

之前没暴露，是因为只有秋招一个模块带迁移。todo 一带上迁移就踩中了：todo 在注册表里
排在秋招前面，时间戳更新，秋招的表就没建出来。

修法是 `runMigrationsFrom` 按目录派生一张专属记账表。这也让「删模块 = 删一个目录」
更完整：模块的迁移记账随它自己走，不留在公共表里。回归测试在
`packages/data/src/module-migrations.test.ts`。

**升级注意：** 已有的本地库仍把模块迁移记在旧的公共表里，新表是空的，会尝试重跑
建表语句而失败。本地库是 gitignored 的开发数据，删掉 `data/local/workbench.db`
重来即可（CLAUDE.md 一直如此约定）。

### 6. 领域错误映射成 4xx

三个新子系统的校验放在 service 而非 route（为了能被集成测试直接覆盖），代价是抛出的
错误默认落到统一错误出口变成 500——冒烟时真的踩到：标签重名报成了服务器故障，还白白
生成一个请求编号。

`server/errors.ts` 的 `DomainError` + `toHttp` 是那座桥。**未知错误必须继续冒泡**，
才能拿到请求编号并落进日志。

## 影响

- todo 从零自有表变成 4 张表，`migrations` 不再是空数组，模块定义从常量导出改为
  接收 Repository 的工厂函数（与秋招同形，ADR-0008）
- `TaskView` 新增 `notes` / `subtasks` / `tags` / `recurrenceId` 四个字段。
  对工作台是安全的——Zod 的 `z.object` 默认剥掉多余键
- 三条铁律未破：core 一行未改，模块间零依赖，迁移随模块走

## 遗留

- **UI 全部缺席。** todo 没有自己的页面，这四项能力目前只有 HTTP 接口。
  界面归工作台的 `TodayPage.tsx`（另一人负责），交接前用户看不到任何变化。
- 标签跨模块筛选（见决策 2）
- 重复规则改节奏（`freq` / `interval`）目前只能删了重建（见决策 3）
