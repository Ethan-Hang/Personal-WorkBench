# 0018. 设置项全链路落库与壳层第二条注册通道

日期：2026-08-19  
状态：已接受

## 背景

主题模式、调色盘、时区、夏令时模式及工作台偏好（问候语、自动展开逾期、动效、完成任务展示等共 8 项设置）此前仅存放于前端浏览器的 `localStorage` 中，未持久化至后端数据库。

这导致两个严重后果：

1. **多端/云端同步撕裂**：当数据上云或换设备时，事项与实体数据虽已同步，但用户个性化偏好不同步；
2. **时区重复猜测**：ADR-0014 中的时区三方推导引擎在新设备首次打开时会重新猜测本地时区，覆盖用户此前明确选定的全局时区。

## 决策

### 一、设置是「壳层子系统」，不是模块

设置不属于任何业务模块（无模块归属），也没有 core `Item` 实体，且外壳启动前即需就绪（`SettingsProvider` 包裹在最外层）。若将其强行包装为业务模块：

- `packages/ui` 将不得不反向依赖模块，破坏分层依赖方向；
- 模块生命周期由路由驱动，而主题/时区需在路由解析前完成首屏注入。

因此，设置作为**壳层子系统**：

- `packages/core`：持有单一真相的 `SETTINGS_CODECS` 编解码器表、纯函数校验器以及 `SettingsRepository` 抽象接口；
- `packages/data`：创建 `app_settings` KV 表与 `SqliteSettingsRepository` 实现；
- `packages/server`：在 `buildApp` 中与 `/api/health` 并排注册 `/api/settings`；
- `packages/ui`：提供框架无关的 `SettingsSync` 同步器（首屏快照、乐观更新、合并串行、失败回滚）与 `SettingsProvider`；
- `packages/web`：实现 `createHttpSettingsStore`，负责快照管理与一次性平滑迁移。

### 二、第二条注册通道的严格判据（防架构退化）

我们在 `buildApp` 中直接注册了 `/api/settings`，这是模块注册表之外的**第二条注册通道**。

为了防止此通道成为「懒得写模块就往这儿塞」的后门，**必须严格满足以下三条判据，缺一不可**：

1. **无 core Item**：不生产、不投影、也不操作任何统一事项；
2. **无模块归属**：逻辑属于全局外壳基座，而非特定业务域；
3. **外壳启动即需要**：渲染首屏前必须立即可用，早于任何模块路由的装载。

目前全系统**只有设置一项**符合该判据。其余任何新功能必须严格按业务模块规范编写。

### 三、KV 表选型与 EAV 否决的边界

采用 `app_settings` 键值对表（`key` TEXT PK, `value_json` TEXT NOT NULL, `updated_at` TEXT NOT NULL）而非单行宽表：

- 设置项是系统中增长与变更最频繁的配置，宽表意味着新增或微调设置项均需执行 `db:generate` 数据库迁移；
- 设置项永远是整表加载并在内存中通过 core 的 `resolveSettings` 进行类型解析与清洗，**从不参与 SQL 层的 WHERE / ORDER BY 筛选**。

**与 ADR 中对 EAV 否决的界限**：
ADR 否决 EAV 针对的是**业务实体**（如 Task、Interview 等），因为实体需进行复杂的关联查询、排序与索引，EAV 会严重损害 SQL 性能与类型安全；而设置项只作为配置存储，应用层通过 core codec 完整保住了强类型安全与默认值回落保障。

### 四、单一真相，不引 Zod

服务端的入参校验、响应结构以及客户端的响应解析，全量复用 `@workbench/core` 的 `SETTINGS_CODECS` 纯函数。不在 server 重复编写 Zod schema，杜绝双份口径导致的漂移。

## 后果

1. **多设备无缝同步**：设置随数据库一同落库，换设备或上云后主题与时区偏好完全一致；
2. **时区免重推**：ADR-0014 的时区推导仅在 `app_settings` 缺失 `timezone.id` 时生效；
3. **首屏零闪烁**：`localStorage` 降级为首屏快照（单键 `workbench_settings`），网络加载完成后后台校正；
4. **强一致性与防御性回滚**：写失败时立即回滚至服务端确认值并显示请求编号，不出现前端假成功。
